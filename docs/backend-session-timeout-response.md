## 1. 요약

요청서의 2절과 3절을 모두 반영해 장치(192.168.0.150)에 배포했습니다. 요청서 5절의 확인 방법대로 장치에서 시험했고 모두 통과했습니다.

| 요청 | 결과 |
|---|---|
| 2.1 세션 만료 | 반영. 요청서 내용 그대로 |
| 2.2 현재 비밀번호 틀림 401 → 400 | 반영. 본문은 그대로 |
| 3-1 비활성화·잠금한 사용자의 토큰 | 바로 무효화. 삭제한 사용자도 함께 고쳤습니다(아래 3절) |
| 3-2 비밀번호 변경 시 다른 세션 | 끝냄. 요청을 보낸 토큰만 유지 |

요청서에 없던 문제도 하나 같이 고쳤습니다. `GET /api/users/security-policy`가 `PUT` 뒤에도 장치를 재시작하기 전까지 예전 값을 돌려주던 문제입니다(4절).

## 2. 동작

- 인증이 필요한 요청(`GET /api/session` 포함)이 올 때마다 토큰의 마지막 사용 시각이 갱신됩니다.
- `sessionTimeoutMinutes` 동안 인증 요청이 없으면 그 토큰은 무효가 되고 **401**입니다(본문 없음, 지금의 "토큰 없음"과 같음).
- `autoLogout`과 상관없이 항상 적용됩니다. 서버는 `autoLogout`을 보지 않습니다. 2단계(웹의 무조작 로그아웃) 켜기·끄기용으로 그대로 쓰시면 됩니다.
- 정책을 바꾸면 이미 발급된 토큰에도 바로 새 시간이 적용됩니다.
- 시간은 장치 부팅 후 경과 시간으로 잽니다. NTP 동기화나 수동 시간 설정으로 시계가 바뀌어도 세션이 한꺼번에 끊기지 않습니다.
- 만료된 세션은 요청이 왔을 때, 그리고 누군가 로그인할 때 정리합니다. 장치 로그에 `INFO Session expired: <username>`이 남습니다.
- 바뀌지 않은 것: `POST /api/logout`은 만료된 토큰으로도 200, swr을 재시작하면 모든 토큰이 무효입니다.

## 3. 3절 질문에 대한 답

**3-1. 비활성화·잠금·삭제:** 반영 전에는 세 경우 모두 토큰이 계속 유효했습니다.

- 장치에서 시험해 보니, 비활성화한 뒤에도, 삭제한 뒤에도 그 토큰으로 `/api/session`과 `/api/dashboard`가 **200**이었습니다.
- 요청서에는 "삭제는 이미 401"이라고 되어 있지만, 실제로는 Manager 이상 권한이 필요한 API에서만 401이었습니다. `Any` 권한 API는 사용자 정보를 DB에서 확인하지 않아서 통과했습니다.

이제는 다음과 같이 바로 무효가 됩니다.

| 경우 | 무효가 되는 토큰 |
|---|---|
| `PUT /api/users/{username}/status`로 `disabled` 또는 `locked` | 그 사용자의 모든 토큰 |
| `DELETE /api/users/{username}` | 그 사용자의 모든 토큰 |
| 로그인 실패가 쌓여 자동 잠금 | **끊지 않음** (새 로그인만 막힘) |

자동 잠금 때 끊지 않는 이유: 사용자 이름만 알면 누구나 틀린 비밀번호를 몇 번 넣어 잠금을 걸 수 있습니다. 그것만으로 켜 둔 관제 화면이 끊기면 안 되기 때문입니다.

**3-2. 비밀번호 변경:** 다른 세션을 끝내도록 했습니다.

| 누가 바꾸나 | 무효가 되는 토큰 |
|---|---|
| 본인 | 그 사용자의 다른 토큰. **요청을 보낸 토큰은 유지**되므로 바꾼 화면은 로그인 상태 그대로입니다 |
| 관리자가 다른 사용자의 것 | 그 사용자의 모든 토큰 |
| 관리자가 자기 것 | 본인과 같음 |

## 4. 함께 고친 것: 보안 정책 `GET`이 예전 값을 돌려줌

- **증상:** `PUT /api/users/security-policy`로 바꾼 직후에도 `GET`은 장치를 재시작하기 전 값을 돌려줬습니다. 비밀번호 최소 길이 검사(`POST /api/users`, 비밀번호 변경)도 예전 값을 썼습니다.
- **원인:** 백엔드가 부팅할 때 읽어 둔 설정을 그대로 쓰고, `PUT`은 설정 파일만 고쳤기 때문입니다.
- **조치:** 이 세 곳은 이제 매번 설정 파일에서 읽습니다. 설정 화면에서 저장한 뒤 다시 열면 저장한 값이 보입니다.

## 5. 프론트에서 할 일

1. **비밀번호 변경 401 예외 제거:** `apiFetch`에서 비밀번호 변경 경로를 401 처리에서 빼 두셨는데, 이제 401이 오지 않으므로 지우시면 됩니다. "현재 비밀번호가 틀림"은 400 + `Current password is incorrect`로 구분하세요.
2. **"세션 만료" 문구:** 이제 만료가 아닌 이유로도 401이 옵니다. 관리자가 비활성화·잠금·삭제한 경우, 다른 곳에서 비밀번호를 바꾼 경우입니다. 지금 문구("세션이 만료되었습니다. 다시 로그인하세요.")로도 괜찮지만, 필요하면 "로그인이 끝났습니다" 같은 넓은 표현을 검토해 주세요. 서버는 이유를 구분해서 알려 주지 않습니다.
3. **자동 요청이 없는 화면:** 서버 만료는 "인증 요청이 없는 시간"으로 판단합니다.
   - 설정 화면처럼 자동으로 요청을 보내지 않는 화면에서 오래 입력하다 저장하면 401을 받고 로그인 화면으로 이동해 입력한 내용을 잃을 수 있습니다(현재 정책 10분).
   - 그런 화면이 있는지 확인해 주세요.
   - 필요하면 그 화면에서도 가볍게 `GET /api/session`을 주기적으로 보내면 됩니다.
4. **본인 비활성화:** Manager가 자기 계정을 `disabled`나 `locked`로 바꾸면, 응답은 200이고 다음 요청부터 401입니다. 화면에서 막고 있지 않다면 막는 것을 권합니다.
5. **문서:** `docs/policy/user-management.md`의 체크리스트 "6. 세션 타임아웃"을 갱신해 주세요. 프론트 담당 문서라 백엔드는 손대지 않았습니다. 체크리스트에 적힌 `QTimer` 주기 정리는 쓰지 않고, 요청과 로그인 때 정리합니다.

## 7. 참고: 장치 상태

- 배포하면서 swr이 두 번 재시작했습니다. 그때 로그인되어 있던 토큰은 모두 무효가 되었고, 트렌드 기록도 멈췄습니다.
- 트렌드 기록은 `261111_151012.tnd`(1초 주기)로 새로 시작해 두었습니다. 이전 파일 `261111_144522.tnd`는 15:06에 끝났습니다. 두 배포 사이에 잠깐 기록된 `261111_150935.tnd`(레코드 22개)는 지워도 됩니다.

## 8. 별도 작업 예정: 백업·복원이 부팅할 때 설정을 씀

4절과 같은 원인으로 백업·복원에도 문제가 있습니다. 이번 작업에서는 고치지 않았고, 백엔드에서 따로 고칠 예정입니다.

- **백업:** 백업 파일의 설정 부분에 부팅할 때의 값이 들어갑니다. 부팅 뒤에 바꾼 설정은 장치를 재시작하기 전에는 백업에 반영되지 않습니다.
- **복원:** 부팅 뒤에 바꾼 트렌드 채널, HMI 화면 수 제한, 언어 설정이 부팅할 때 값으로 되돌아갈 수 있습니다.

고치기 전까지는 설정을 바꿨다면 백업하기 전에 장치를 재시작하는 것이 안전합니다. 고치면 API 변경 이력에 알리겠습니다.
