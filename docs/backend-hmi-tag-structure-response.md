# HMI 태그 구조 — 백엔드 답변

> 작성: 2026-11-24 (백엔드)
> 대상: 프론트엔드
> 관련: `docs/backend-hmi-tag-structure-request.md`(요청서), `docs/architecture/hmi.md`
> 이 문서의 "요청서 2.x / 질문 n"은 요청서의 절과 3장 질문 번호입니다.

---

## 1. 요약

요청서 2장의 방향(4개 층, `kind` 3종, JSON AST, 계산은 백엔드 한 곳)에 **동의합니다.** 지금 백엔드 구조와 크게 부딪히는 곳은 없습니다.

다만 두 가지는 요청서와 다르게 제안합니다.

1. **계산 시점:** 폴링 묶음이 끝날 때가 아니라 **`GET /api/hmi/values`를 받을 때** 계산합니다(질문 2). 백엔드에는 "폴링 묶음"이라는 단위가 없고, 품질도 읽는 시각에 정해지기 때문입니다.
2. **레지스터를 지울 때:** 태그를 직접 지울 때는 거부(409)하는 데 동의합니다. 다만 레지스터·장비 삭제, 복원, 가져오기는 막지 않습니다. 그때 참조가 끊긴 expr 태그는 지우지 않고 남겨 두며, 값은 `bad`로 내립니다(질문 1).

가장 큰 구현 비용은 **`hmi_tags` 테이블을 새로 만드는 마이그레이션**입니다(질문 7). 단계 B 구현 요청을 받으면 이 마이그레이션부터 합니다.

## 2. 요청서 2장에 대한 의견

| 절 | 의견 |
|---|---|
| 2.1 `kind` | 동의. 값이 없으면 `register`로 읽습니다. 태그 ID는 문자이고 바꿀 수 없다는 점, `valueType` 3종도 동의합니다 |
| 2.2 AST | 동의. 노드 3종, 연산자 이름, 등록부 방식 모두 그대로 받습니다. 저장할 때 거부할 항목에 **크기 한도 초과**를 더합니다(질문 2의 한도) |
| 2.3 변환 함수 | 동의. 질문 3 참고 |
| 2.4 응답 형식 | 동의. register 태그는 지금 그대로 `raw`, expr·param 태그는 `value`입니다. expr·param 태그에는 `unit`·`access`도 같이 줍니다(param은 `rw`, expr은 `r`) |
| 2.5 엔진·품질 | 품질 규칙은 동의합니다. 계산 시점은 질문 2처럼 바꿉니다. 정상 입력이 있어도 아래 경우는 `bad`로 봅니다: 참조한 태그가 없음, register 태그의 `raw`가 `null`(여러 워드 등), 타입이 맞지 않음, 0으로 나눔 |
| 2.6 평가 API·시험 데이터 | 동의. 위치는 `referencs/`로 하고, 초안은 프론트가 써 주세요. 백엔드 단위 시험도 같은 파일을 읽습니다 |
| 2.7 하지 않을 것 | 동의. `widget_bindings` 표를 만들지 않는 것은 백엔드에도 이득입니다(화면 JSON은 지금처럼 해석하지 않음) |

## 3. 질문에 대한 답변

### 질문 1. 참조 중인 태그 삭제

| 경우 | 처리 |
|---|---|
| `DELETE /api/hmi/tags/{id}` | **거부.** 409와 함께 `{ "error": ..., "referencedBy": ["RUNNING", ...] }`를 돌려줍니다 |
| expr 태그를 저장할 때 없는 태그를 참조 | 거부(422) |
| 레지스터·장비 삭제 → register 태그 연쇄 삭제 | **막지 않음.** 그 태그를 참조하던 expr 태그는 남고, 값은 `bad`입니다 |
| 시스템 복원, HMI 가져오기에서 레지스터가 없어 register 태그를 건너뜀 | 위와 같음. 참조가 끊긴 expr 태그는 경고 목록에 이름을 넣습니다 |

레지스터 삭제까지 막지 않는 이유는 다음과 같습니다.

- 레지스터 삭제 → HMI 태그 연쇄 삭제는 지금 DB 외래 키(`ON DELETE CASCADE`)가 처리합니다. 장비 삭제, 레지스터 일괄 교체, 복원 모두 이 경로를 씁니다.
- 이 경로마다 "HMI 식이 참조 중이면 거부"를 넣으면, 레지스터 화면에서 HMI 때문에 작업이 막히는 경우가 생깁니다. 사용자는 HMI 편집기로 가서 식부터 고쳐야 합니다.
- 식 안의 참조는 JSON 속에 있어서 외래 키로 표현할 수 없습니다. 거부하려면 경로마다 따로 코드를 넣어야 합니다.

그래서 **"참조가 끊긴 expr 태그는 남고 값은 `bad`"**를 정상 상태의 하나로 받아들이자는 제안입니다. 편집기가 이 상태를 보여 줄 수 있도록 `GET /api/hmi/tags`의 expr 태그에 `missingRefs: ["TAG_A"]`(비어 있으면 `[]`)를 줍니다.

### 질문 2. 계산 시점과 부하

**요청을 받을 때 계산하기를 제안합니다.** `GET /api/hmi/values`가 요청한 태그와 그 태그가 참조하는 태그만 그 자리에서 계산합니다.

| 근거 | 내용 |
|---|---|
| 폴링 묶음이 없음 | 폴링은 RS-485 버스마다, TCP 장비마다 따로 도는 스레드입니다. 모든 장비를 한 번 다 읽은 시점이라는 것이 없습니다 |
| 품질은 읽는 시각에 정해짐 | `good`/`normal`/`bad`는 마지막 수신 시각과 지금 시각의 차이로 정합니다(지금 register 태그도 같음). 폴링 때 계산해 두면 통신이 끊긴 뒤에도 결과가 `good`으로 남습니다 |
| 지금 구조와 같음 | 지금 `values`도 요청마다 레지스터 표에서 값을 읽어 만듭니다. 계산 결과 캐시와 스레드 사이 동기화를 새로 만들 필요가 없습니다 |
| 일관성 | 한 요청 안에서 같은 시각, 같은 입력값으로 계산합니다. 같은 태그는 한 번만 계산합니다 |
| 부하 | 비교·논리 식은 노드 하나에 마이크로초 단위입니다. HMI 화면이 1초마다 부르는 정도는 문제가 되지 않습니다 |

같이 하는 일은 다음과 같습니다.

- 태그 목록을 요청마다 DB에서 읽지 않고, 메모리에 캐시합니다. 식은 저장할 때 한 번만 해석해 둡니다. 태그를 바꾸면 캐시를 새로 만듭니다.

**한도(i.MX6ULL 기준, 저장할 때 검사):**

| 항목 | 한도 | 넘으면 |
|---|---|---|
| 전체 HMI 태그 | 1,000개 | 422 |
| 식 하나의 노드 수 | 64개 | 422 |
| 식 하나가 참조하는 태그 | 32개 | 422 |
| expr → expr 참조 깊이 | 8단 | 422 |

숫자는 넉넉하게 잡았습니다. 실제 화면을 만들다가 부족하면 늘리겠습니다.

**나중에 바뀔 수 있는 점:** expr 태그 값을 경보, 트렌드, Modbus 서버에서도 써야 하면 그때는 주기적으로 계산하는 백그라운드 방식이 필요합니다. AST 형식과 API는 그대로 두고 내부만 바꾸면 됩니다. 지금 범위(HMI 화면 전용)에서는 필요 없습니다.

### 질문 3. 표시 값 변환의 기준

백엔드에 두는 데 문제가 없습니다.

- **예전 `scaledValue`와의 관계:** 예전 코드는 폴링할 때 모든 레지스터의 표시 값을 미리 계산해 응답에 실었습니다(11-13 HMI, 11-20 실시간에서 제거). 이번 함수는 그것을 되살리는 것이 아닙니다. **계산 엔진과 쓰기 범위 검사 안에서만 쓰는 순수 함수**이고, 응답에는 실리지 않습니다. 원본 데이터 원칙은 그대로입니다.
- **함수의 정의:** `원본 → (isSigned면 2의 보수) → × 배율 (태그 scale이 있으면 태그 것, 없으면 레지스터 것)`입니다. 코일·접점은 0/1을 그대로 씁니다. 오프셋은 태그 설정에 생기면 이 함수에만 더합니다.
- **확인 방법:** 요청서 2.6의 변환 표를 백엔드 단위 시험이 그대로 읽어 프론트 `WHMI.raw`와 같은 결과인지 확인합니다.

### 질문 4. 쓰기 범위 검사

**동의합니다.** 단계 B에서 변환 함수가 생기면 `POST /api/hmi/write`에 넣겠습니다.

- 받은 `raw`를 변환 함수로 표시 값으로 바꾼 뒤, 태그 `min`/`max`와 비교합니다. 태그 값이 비어 있으면 레지스터 `minValue`/`maxValue`와 비교합니다(±1.797…e308은 제한 없음).
- 범위 밖이면 422 `{ "error": ..., "min": ..., "max": ..., "value": ... }`를 돌려줍니다.
- param 태그 쓰기도 같은 규칙을 따릅니다(아래 질문 7 참고).
- 위젯의 "조작 허용 조건"을 서버가 강제하지 않는 것도 동의합니다.

### 질문 5. 여러 워드 레지스터

방향에 동의합니다. `values`의 register 태그에 실시간 API와 같은 형식의 `rawWords`를 주겠습니다. 1워드 태그의 `raw`는 그대로 둡니다.

- 변환 함수도 실시간 API 명세와 같은 규칙(상위 워드부터 이어 붙임, 전체 비트 수 기준 2의 보수)으로 넓힙니다.
- 여러 워드 **쓰기**는 별도로 정합니다(지금 `POST /api/hmi/write`는 1워드만 받음).
- 급하지 않으면 단계 B와 따로 진행하기를 권합니다.

### 질문 6. 내보내기 파일 버전

**`schemaVersion`은 1로 둡니다.** 지금 확인한 동작은 다음과 같습니다.

- **예전 파일 → 새 펌웨어:** 예전 파일에는 `kind`가 없으므로 모두 `register`로 읽습니다. 문제가 없습니다.
- **새 파일 → 예전 펌웨어:** 지금 가져오기는 태그를 `unifiedAddress`로 레지스터에 연결합니다. 연결할 레지스터가 없는 태그는 **이미 건너뛰고 경고에 이름을 넣습니다.** expr·param 태그는 `unifiedAddress`가 없으므로 예전 펌웨어에서는 자동으로 건너뜁니다. 화면에서는 "없는 태그"로 보입니다.
- **새 펌웨어가 모르는 `kind`를 만나면:** 건너뛰고 경고에 넣는 것으로 정합니다.

시스템 백업의 `hmi.json`도 같은 규칙을 따릅니다. param 태그는 정의와 함께 **현재 값**도 내보내기·백업에 넣습니다(복원하면 설정값이 돌아옴).

### 질문 7. DB 구조 변경

**컬럼을 추가하고, 테이블은 새로 만듭니다.** `source` 전체를 JSON 한 칸으로 바꾸지는 않습니다.

```sql
hmi_tags (
  id, name, unit, min_value, max_value, scale, access, created_at, updated_at,   -- 지금 그대로
  kind        TEXT NOT NULL DEFAULT 'register' CHECK(kind IN ('register','expr','param')),
  register_id INTEGER REFERENCES registers(id) ON DELETE CASCADE,   -- NOT NULL 해제
  value_type  TEXT,      -- expr·param: 'bool' | 'number' | 'string'
  expr        TEXT,      -- expr: AST JSON
  param_init  TEXT,      -- param: 초기값 JSON
  param_value TEXT,      -- param: 현재 값 JSON
  CHECK ((kind = 'register') = (register_id IS NOT NULL))
)
```

- **register 태그는 지금처럼 외래 키 연쇄 삭제를 유지합니다.** 그래서 `register_id` 컬럼은 남기고 NOT NULL만 풉니다.
- SQLite는 이미 있는 컬럼의 NOT NULL을 풀 수 없습니다. 그래서 "새 테이블 만들기 → 옮기기 → 이름 바꾸기"를 한 트랜잭션으로 하는 마이그레이션이 필요합니다. 기존 데이터는 모두 `kind='register'`로 옮겨지고, 사용자 쪽에서 할 일은 없습니다.
- **API 형식은 요청서 그대로입니다.** 요청 바디는 `source`(kind별)로 받고, DB 컬럼은 내부 구현입니다.
  - register 태그 응답의 `source`에는 지금처럼 장비·레지스터 정보를 덧붙입니다.
- **param 값 쓰기:** `POST /api/hmi/write`에 `{ "tag": "ALM_LIMIT", "value": 85 }`로 받고 DB에 저장하기를 제안합니다(register 태그는 지금처럼 `raw`). 사용자가 직접 바꿀 때만 쓰므로 플래시 쓰기 횟수는 문제가 되지 않습니다. 정확한 바디는 단계 C 요청서에서 정해 주세요.

### 질문 8. 그 밖에 백엔드 구조와 맞춰 둘 점

1. **복원에서 "장비만 복원, HMI는 유지":** 지금은 register 태그를 `unifiedAddress`로 새 레지스터에 다시 연결합니다. expr·param 태그는 레지스터와 무관하므로 그대로 남깁니다. 다시 연결하지 못한 register 태그를 참조하는 expr 태그는 질문 1처럼 `bad`가 되고, 경고에 이름이 들어갑니다.
2. **HMI 가져오기 순서:** register 태그 → param 태그 → expr 태그 순으로 넣고, expr 태그는 마지막에 순환·한도를 검사합니다. 가져오는 파일 안에서 순환이 있으면 **가져오기 전체를 거부**합니다(일부만 들어가면 결과를 예측하기 어려움).
3. **평가 API:** `POST /api/hmi/eval`(경로는 단계 B 요청서에서 확정)을 제안합니다.
   - 권한은 로그인한 사용자 누구나입니다.
   - 바디 한도는 화면 저장과 같은 수준으로 둡니다.
   - 생략한 입력은 현재 값을 씁니다. `inputs`에 준 값은 register 태그라도 **원본(`raw`)으로** 받습니다. 그래야 변환 함수까지 함께 시험됩니다.
4. **스레드:** HTTP 처리는 메인 스레드, 폴링은 버스·장비별 스레드이고, 레지스터 표는 잠금으로 보호됩니다. 요청 시 계산 방식이면 새 스레드나 공유 캐시가 생기지 않아 충돌할 부분이 없습니다.
