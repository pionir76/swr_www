## 1. 목표와 전제

HMI는 장비 값을 그래픽 화면으로 보여 주고 조작하는 기능이다(`#hmi` 페이지). 사용자가 화면을 직접 그리고(디자인 모드), 실제 값으로 동작시킨다(실행 모드).

설계 전제(2026-11-24 사용자·타 팀 협의 결과):

1. HMI의 초기 자료구조는 앞으로의 확장에 기초가 된다. **단순하되 역할별로 확실히 나뉘어** 있어야 기능이 늘어나도 구조를 바꾸지 않고 받을 수 있다.
2. 자료구조는 **사용자 요구에 유연하게** 대응할 수 있어야 한다.

이 두 전제에서 나온 답이 아래의 "4개 층" 구조다. 새 기능은 정해진 자리에 끼워 넣는다.

| 늘어나는 것 | 끼우는 자리 |
|---|---|
| 새 연산(예: 평균, 히스테리시스) | 연산자 등록부에 한 줄 (§5.3) |
| 새 태그 종류 | 태그 `kind` 하나 (§5.2) |
| 새 위젯 상태(예: 깜빡임) | 위젯 상태 칸 하나 (§5.5) |
| 새 위젯 | 위젯 목록과 속성 정의 (`hmi-widgets.md`) |

## 2. 전체 개념도

```
 ┌──────────────────────────────────────────────────────────────────────┐
 │ ① 통신 층 — 레지스터                         (백엔드, 레지스터 관리 화면) │
 │    장비·주소·워드 수·부호·바이트 순서. "어디서 어떻게 읽나"                │
 │    결과는 원본 워드 그대로 (raw)                                         │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 │ registerId 로 참조
 ┌───────────────────────────────▼──────────────────────────────────────┐
 │ ② 태그 층 — HMI 태그                          (백엔드 저장, 태그 관리 화면) │
 │    "그 값을 무엇이라 부르고 어떻게 보나"                                  │
 │                                                                      │
 │    register 태그 ── 레지스터 하나 + 표시 설정(배율·단위·범위·권한)        │
 │    expr 태그   ──── 다른 태그로 계산하는 식(AST)       예: RUNNING       │
 │    param 태그  ──── 사용자가 HMI에서 정하는 설정값      예: 경보 기준 80   │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 │ 태그 ID 로 참조
 ┌───────────────────────────────▼──────────────────────────────────────┐
 │ ③ 계산 층 — 엔진                                                      │
 │    백엔드: expr 태그 계산(값 요청 때, 순환 거부, 품질 전파)                │
 │    프론트: 원본 → 표시 값 변환, 위젯 조건 판정(whmi-rules.js)             │
 └───────────────────────────────┬──────────────────────────────────────┘
                                 │ 값 + 품질(q)
 ┌───────────────────────────────▼──────────────────────────────────────┐
 │ ④ 표시 층 — 화면과 위젯                        (백엔드 저장, 편집기 화면) │
 │    위젯 = 태그를 보여 주는 화면 객체. 램프는 Bool을 보여 주는 위젯일 뿐    │
 │    tag(값) · writeTag(쓰기) · visibleWhen/enableWhen/activeWhen(상태)    │
 └──────────────────────────────────────────────────────────────────────┘
```

| 층 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| ① 레지스터 | 통신, 데이터 해석에 필요한 형식(워드 수·부호·순서) | 이름 붙이기, 화면 표시 |
| ② 태그 | 의미(ID·이름), 표시 설정, 계산 식, 설정값 | 통신 설정(장비·주소·기능 코드는 두지 않음) |
| ③ 엔진 | 계산, 판정, 품질 전파 | 저장 |
| ④ 화면 | 배치, 모양, 어느 태그를 어디에 쓸지 | 조건 조합(복잡한 판단은 expr 태그로) |

## 3. 용어

| 용어 | 뜻 |
|---|---|
| 레지스터 | 장비의 통신 지점(①). 자기 `tagName`이 있지만 HMI 태그와는 별개 |
| HMI 태그 | ②의 모든 태그. 레지스터 `tagName`과 독립된 네임스페이스 |
| register 태그 | 레지스터 하나를 가리키는 HMI 태그. 화면 표기는 "레지스터" |
| expr 태그(계산 태그) | 식으로 값을 계산하는 태그. 예전 이름 "가상 태그". **화면 표기는 "로직"** |
| param 태그(설정 태그) | 사용자가 HMI에서 바꾸는 설정값. 장비와 무관. 화면 표기는 "설정"(준비 중) |
| 원본(raw) | 장비에서 읽은 워드 그대로(uint16) |
| 표시 값 | 원본에 부호·배율·오프셋을 적용한 값 |
| 조건 | "태그 하나 + 비교 하나". 위젯 상태 칸이 쓰는 작은 식 |
| 식(AST) | 조건을 묶고 계산하는 나무 구조. expr 태그가 쓰는 큰 식 |
| 품질(q) | 값을 믿을 수 있는지: `good` / `normal` / `bad` / `disabled` |

## 4. 원칙

1. **역할 분리.** 통신은 레지스터, 의미는 태그, 계산은 엔진, 모양은 위젯. 한 정보는 한 곳에만 정의한다.
2. **원본 데이터 원칙**(`overview.md` §5.1). 통신 원본은 원본 그대로 저장·전송한다. 원본 → 표시 값 변환 규칙(부호·배율·오프셋)은 태그 설정으로 정해지는 **하나의 함수**다.
   - 프론트는 화면 표시·쓰기 역변환에, 백엔드 계산 엔진은 expr 태그 평가에 같은 함수를 쓴다.
   - 두 구현이 같은 결과를 내도록 공통 시험 데이터(원본 → 기대 값 표)로 함께 검증한다.
   - register 태그 값은 계속 원본으로 내려간다. expr·param 태그 값은 원본이 아니므로 `value`로 내려간다(§5.4).
3. **스크립트 없음.** 정해진 연산자만 쓴다(연산자 등록부). 화면 설정이 프로그래밍이 되지 않게 한다.
4. **위젯 조건은 태그 하나 + 비교 하나.** 여러 조건의 조합은 이름 붙은 expr 태그로 모은다. 재사용·점검·사용처 추적이 쉬워진다.
5. **계산형만.** 사건이 생길 때만 바뀌고 값을 기억하는 변수(사건 기반 변수)는 두지 않는다. 사건을 놓치면(현장 조작, 통신 단절, 재시작) 장비와 어긋난다. param 태그는 사용자가 직접 쓸 때만 바뀌는 설정값이라 이 원칙과 충돌하지 않는다.
6. **안전 인터록이 아니다.** 조작 허용 조건과 계산 태그는 화면 편의일 뿐이다. 실제 보호 로직은 PLC·제어기에 있어야 한다(편집기 도움말에도 표시).
7. **저장 원본은 데이터(JSON)다.** 식은 AST로 저장하고, 화면에 보이는 수식 글자는 AST에서 만들어 보여 주기만 한다.
8. **효용 대비 비용.** 효과보다 코드 복잡성이 커지는 기능은 의견부터 제시하고 승인 후 진행한다.
9. **한 가지는 한 곳에서 정한다(UI도).** 단위·소수점·입력 범위는 태그에서, "언제 켜지나"는 조건 한 칸에서, 시작 화면은 편집기에서. 같은 것을 정하는 칸을 두 곳에 두지 않는다.

### 4.1 프론트와 백엔드의 경계

> **"태그 값이 무엇인가"는 백엔드, "그 값을 어떻게 보이나"는 프론트.**

| 일 | 맡는 곳 | 비고 |
|---|---|---|
| 통신, 원본 값, 품질 | 백엔드 | |
| 태그 사이의 계산·조합(expr 태그), 순환 검사 | 백엔드 | 미리보기도 백엔드 평가 API |
| 쓰기 수행, 권한(`access`), **쓰기 범위 검사** | 백엔드 | 범위 검사는 단계 B에서 서버에 들어감(합의됨). 프론트 입력 창 검사는 편의용으로 남김 |
| 소수점·단위 붙이기(원본 → 표시 값) | 프론트 | 표시 형식. 같은 변환 함수를 계산 엔진도 쓰므로 공통 시험 데이터로 검증 |
| 한 태그 값 → 모양(구간 색, 상태 글자, 켜짐 모습, 보이기) | 프론트 | 위젯 조건 "태그 하나 + 비교 하나"(판정 엔진 §5.6) |
| 조작 허용 조건(`enableWhen`) | 프론트 | **화면 편의일 뿐, 서버는 강제하지 않는다**(원칙 6) |
| 태그 점검, 사용처 | 프론트 | 편집 도구 |

**위젯 조건 판정을 프론트에 둔 이유와 대안(2026-11-24 결정: B안).** 모든 조건을 계산 태그로만 만드는 방식(A안: 위젯은 참/거짓 태그만 가리킴)은 판정이 한 곳에 모이지만, 램프 하나·비트 하나마다 태그를 만들어야 한다. 그래서 한 줄 조건은 위젯에 두되(B안), **켜짐 판정을 조건 한 형식(`activeWhen`)으로 통일**해 나중에 A안으로 옮길 때 "조건 하나 → 계산 태그 하나"로 기계적으로 바꿀 수 있게 했다. 같은 비교 규칙이 프론트 엔진과 백엔드 엔진 두 곳에 있으므로 공통 시험 데이터로 맞춘다.

## 5. 자료구조

### 5.1 레지스터 (① 통신 층)

`referencs/api-spec.md` §5. HMI 관점에서 쓰는 필드: `id`, `deviceId`, `tagName`, `unifiedAddress`, `type`(holding_register·input_register·coil·discrete_input), `length`(워드 수), `isSigned`, `scale`, `minValue`/`maxValue`, `readOnly`, 장비 `byteOrder`.

- 데이터 형식(Int32, Float, 바이트·워드 순서)은 **레지스터에서만** 정한다. 태그는 형식을 갖지 않는다.
- 지금 HMI 태그는 1워드 레지스터만 받는다. 여러 워드는 값 응답에 원본 워드 배열(`rawWords`)을 받아 실시간 화면과 같은 해석 함수(`RegFmt`)로 푼다(할 일 C).

### 5.2 HMI 태그 (② 태그 층)

**공통 필드**

```json
{ "id": "RUNNING", "name": "운전중", "kind": "expr",
  "unit": null, "min": null, "max": null, "access": "r",
  "source": { "...": "kind별" } }
```

| 필드 | 규칙 |
|---|---|
| `id` | 영숫자·`_`·`-`, 최대 64자. **만든 뒤 바꿀 수 없다.** 화면과 식이 이 값으로 참조한다 |
| `name` | 표시 이름. 언제든 바꿀 수 있다(참조는 `id`라 영향 없음) |
| `kind` | `register` / `expr` / `param`. **없으면 `register`**(지금 데이터 그대로 호환) |
| `unit`, `min`, `max`, `access` | 표시·쓰기 설정. register 태그는 비우면 레지스터에서 상속 |

ID는 정수가 아니라 문자다. 정수 ID는 장비마다 달라 내보내기·장비 간 복사·화면 JSON에서 충돌한다. 이름 바꾸기 요구는 `name`으로 받는다.

**kind별 `source`와 추가 필드**

| kind | `source` | 추가 필드 | 값 | 쓰기 | 상태 |
|---|---|---|---|---|---|
| `register` | `{ "registerId": 12 }` (+응답 전용 장비·레지스터 정보) | `scale`(원본 기준, 비우면 상속), `offset`(할 일 C) | 원본 `raw` → 프론트가 표시 값으로 | `access: rw`면 원본으로 씀 | **구현됨** |
| `expr` | `{ "valueType": "bool", "expr": { AST } }` | — | 백엔드가 계산한 `value` | 불가(읽기 전용) | 할 일 B |
| `param` | `{ "valueType": "number", "initial": 80 }` | `min`/`max`로 쓰기 범위 | 저장된 `value` | 사용자 쓰기로만 바뀜 | 할 일 C |

- 값 타입(`valueType`)은 `bool` / `number` / `string` 3종이다. 정수 폭·실수 형식은 레지스터 해석 단계의 일이다.
- register 태그 표시 값 = 원본(부호 해석) × `scale` + `offset`. `offset`은 4–20mA 환산·온도 보정 같은 요구용 선택 항목(비우면 0).

### 5.3 식(AST)

expr 태그의 저장 원본. 노드는 세 가지다.

```json
{ "tag": "NOW_STS" }                 // 태그 참조(문자 ID)
{ "value": 3 }                       // 상수(숫자·문자·참거짓·비트 목록)
{ "op": "and", "args": [ ... ] }     // 연산
```

예: `NOW_STS 비트 1·2 중 하나라도 1` **그리고** `ALSTS = 0`

```json
{ "op": "and", "args": [
  { "op": "bitAny", "args": [ { "tag": "NOW_STS" }, { "value": [1, 2] } ] },
  { "op": "eq",     "args": [ { "tag": "ALSTS" },   { "value": 0 } ] } ] }
```

**연산자 등록부** — 연산자마다 인수 개수·입력 타입·결과 타입·계산 함수·편집기 표시 이름을 한 줄로 정의한다. 연산자 추가 = 등록부에 한 줄.

| 묶음 | 연산자 | 결과 | 단계 |
|---|---|---|---|
| 비교 | `eq` `ne` `gt` `ge` `lt` `le` `range` | bool | B (`eq ne gt lt range`는 프론트 엔진에 이미 있음) |
| 비트 | `bitAny` `bitNone` (비트 0~15, 정수에만) | bool | B (프론트 엔진에 이미 있음) |
| 논리 | `and` `or` `not` (묶음 중첩 가능) | bool | B |
| 선택 | `select` — `[조건, 값, 조건, 값, …, 기본값]` 처음 맞는 값 | 값 | B |
| 산술 | `add` `mul` `min` `max` `avg`(2개 이상) `sub` `div`(2개) `abs`(1개) — 인수는 숫자로 읽고, 숫자가 아니거나 결과가 유한하지 않으면(0으로 나눔·넘침) 판정 불가. 숫자 태그의 `decimals`(0~6, 태그 최상위)가 있으면 최종 결과를 그 자릿수로 반올림 | number | C-2 (구현됨) |
| 시간·상태 | `hysteresis` `ton` `tof` `rising` `latch` | bool | D (노드별 상태·타이머·재시작 정책 필요) |

**계산 규칙**(프론트 판정 엔진 §5.6과 같은 규칙. 기준은 공통 시험 데이터 `referencs/hmi-testdata-expr.json`)

| 항목 | 규칙 |
|---|---|
| 태그 참조의 값 | register 태그는 표시 값(부호·배율 적용), expr·param 태그는 그 값 |
| 비교 | `eq`/`ne`는 둘 다 숫자로 읽히면 숫자 비교, 아니면 글자 비교. `gt ge lt le`는 숫자로 읽힐 때만(아니면 거짓). `range`는 `[값, 최소, 최대]`, 양 끝 포함, `null`이면 끝없음 |
| 비트 | `[값, 비트 목록]`. 값을 정수로 내림해 판정(배율 1인 상태 워드에 쓰는 것이 전제) |
| 논리 | `and` `or` `not`의 인수는 참/거짓으로 읽는다(숫자 0·`false`·빈 글자·글자 `"0"`·`"false"`는 거짓). 태그를 직접 인수로 쓸 수 있다 |
| 선택 | `[조건, 값, 조건, 값, …, 기본값]`. 위에서부터 처음 참인 조건의 값 |
| 결과 | `valueType`이 `bool`이면 참/거짓으로 바꿔 내보냄 |
| 품질 | 식이 참조하는 태그(이어 쓴 태그 포함) 중 하나라도 판정 불가면 결과도 `bad`, 값은 `null`. 지름길 계산을 하지 않는다(`or`의 한쪽이 참이어도 다른 쪽이 `bad`면 `bad`) |

**검증(저장할 때 백엔드가 422로 거부)**: 인수 개수·타입 불일치, 없는 태그 참조, 순환 참조(자기 자신을 거쳐 돌아오는 참조), 비트 범위 밖, 한도 초과.

| 한도(i.MX6ULL 기준) | 값 |
|---|---|
| 전체 HMI 태그 | 1,000개 |
| 식 하나의 노드 | 64개 |
| 식 하나가 참조하는 태그 | 32개 |
| expr → expr 참조 깊이 | 8단 |

**참조가 끊긴 expr 태그**: 참조하던 태그가 레지스터·장비 삭제, 복원, 불러오기로 사라지면 expr 태그는 **남고 값은 `bad`**다(정상 상태의 하나). 태그 목록 응답의 `missingRefs: ["TAG_A"]`로 드러나고 태그 점검이 오류로 보여 준다.

**위젯 조건과의 관계**: 위젯의 조건 `{ "tag": "X", "test": "eq", "value": 1 }`은 `{ "op": "eq", "args": [{ "tag": "X" }, { "value": 1 }] }`의 줄임 모양이다. 같은 연산자 이름을 쓴다.

### 5.4 값과 품질

`GET /api/hmi/values` 응답 한 항목:

| kind | 형식 | 비고 |
|---|---|---|
| register | `{ "raw": 569, "q": "good", "unit": "%", "access": "r" }` | 구현됨. 프론트 `WHMI.raw`가 부호·배율 적용 |
| expr / param | `{ "value": true, "q": "good", "unit": "", "access": "r" }` | 할 일 B·C. 원본이 아니므로 `value`. `access`는 expr `r`, param `rw` |

| q | 뜻 | 화면 |
|---|---|---|
| `good` | 마지막 폴링 경과 < 1.5 × 주기 | 정상 |
| `normal` | 1.5 ~ 3 × 주기(응답 지연) | 값 유지 + 연한 호박색 |
| `bad` | 3 × 초과 또는 응답 없음 | 흐리게, `----` |
| `disabled` | 장비 비활성 | `bad`와 같게 표시(사용자 결정) |

**품질 전파(expr 태그)**: 입력 중 하나라도 `bad`/`disabled`이면 결과도 `bad`. `normal`이 섞이면 `normal`. 마지막 정상값을 들고 있지 않는다. 다음도 `bad`다: 참조한 태그가 없음, register 태그의 원본이 `null`(여러 워드 등), 타입이 맞지 않음, 0으로 나눔.

### 5.5 화면과 위젯 (④ 표시 층)

**프로젝트·화면**: 프로젝트(이름, 시작 화면, 화면 순서, 값 갱신 주기 `pollMs` 500–10000)와 화면 문서(화면별 `content`, `format: "whmi.screen"`)로 저장한다. 화면별 revision으로 충돌을 막는다(§8).

**위젯**

```json
{ "id": "btn_run", "type": "button", "x": 40, "y": 60, "w": 120, "h": 44,
  "tag": "OPMODE", "writeTag": null,
  "props": { "action": "toggle", "onValue": 1, "offValue": 4 },
  "visibleWhen": null,
  "enableWhen": { "tag": "CAN_START", "test": "eq", "value": true },
  "activeWhen": { "tag": "NOW_STS", "test": "bitAny", "bits": [1, 2] } }
```

| 연결 | 뜻 |
|---|---|
| `tag` | 값 표시(그리고 쓰기 대상) 태그. 어떤 kind든 표시 가능. 텍스트 위젯은 태그 값을 글자 그대로, 상태 표시는 값에 맞는 줄의 글자·색을 보여 준다 |
| `writeTag` | 쓰기 대상을 따로 둘 때(예: NSP 표시, TSP 쓰기). expr 태그는 고를 수 없음 |
| `visibleWhen` | 보이기 조건. 거짓이면 숨김, 판정 불가면 보임(정보를 감추지 않음) |
| `enableWhen` | 조작 허용 조건(쓰기 위젯). 거짓·판정 불가면 막음 |
| `activeWhen` | 켜짐 조건(램프·버튼·스위치). **켜짐 판정은 이 칸 하나로 정한다.** 비우면 램프는 값이 참일 때, 버튼·스위치는 현재 값이 켜짐 값(`onValue`, 쓸 값과 같음)일 때 켜짐 |
| `props` | 위젯 모양과 자기 값에 따른 모양 규칙(구간 색, 상태 목록 등). 위젯이 태그 값을 덮어쓰는 것은 눈금 범위(게이지·탱크·막대의 `min`/`max`)뿐 |

- 상태 칸은 지금 3개다. 4번째(예: 깜빡임)가 필요해지면 세 칸과 함께 `bind: { visible, enable, active, blink }` 묶음 하나로 정리한다(할 일 D). 모든 속성 바인딩은 하지 않는다.
- **연결은 화면 문서 안에 둔다.** 별도 DB 표(`widget_bindings`)를 만들지 않는다. 사용처는 편집기가 화면 문서를 읽어 계산한다.
- "상태 칸 + 계산 태그" 방식은 업계 주류와 같다(2026-10-23 조사: WinCC·FactoryTalk·InTouch·CODESYS·Pro-face는 상태 칸 + 조건, Ignition은 속성 바인딩 + 수식 태그).

### 5.6 판정 엔진 (프론트 `js/whmi-rules.js`)

위젯 상태 칸과 위젯별 모양 규칙(램프 켜짐 값·비트, 버튼·스위치 켜짐, 상태 표시 목록, 구간 색)이 모두 이 엔진 하나로 판정한다.

| 항목 | 규칙 |
|---|---|
| 같음 `eq`/`ne` | 두 값이 모두 숫자로 읽히면(참/거짓은 1/0) 숫자 비교, 아니면 글자 비교 |
| 큼·작음 `gt`/`lt` | 숫자로 읽힐 때만. 아니면 거짓 |
| 범위 `range` | `min ≤ 값 ≤ max`(양 끝 포함, 비우면 끝없음) |
| 비트 `bitAny`/`bitNone` | 값을 정수로 내림해 비트 판정. 비트를 안 고르면 거짓 |
| 판정 불가 | 값 없음, `bad`, `disabled` → `null`. 쓰는 쪽이 정해진 기본 결과를 씀(§5.5 표) |
| 대응표 | 위에서부터 처음 맞는 줄. 없으면 "없음", 판정 불가면 `null` |

조건에 나온 태그는 런타임이 자동으로 함께 폴링한다. expr 태그도 일반 태그처럼 조건에 쓸 수 있다(계산은 백엔드).

## 6. 실행 흐름

**백엔드 계산 엔진(할 일 B, 2026-11-24 백엔드 합의)**

- 태그 저장 때 식을 한 번 해석해 두고 순환 참조·한도를 검사한다. 태그 목록은 메모리에 캐시한다.
- **값을 요청받을 때 계산한다.** `GET /api/hmi/values`가 요청한 태그와 그 태그가 참조하는 태그만 그 자리에서 계산한다. 한 요청 안에서는 같은 시각·같은 입력값을 쓰고 같은 태그는 한 번만 계산한다.
  - 백엔드 폴링은 버스·장비별 스레드라 "폴링 묶음" 단위가 없고, 품질은 읽는 시각에 정해지기 때문이다. 미리 계산해 두면 통신이 끊긴 뒤에도 결과가 `good`으로 남는다.
  - expr 태그를 경보·트렌드·Modbus 서버에서 쓰게 되면 주기 계산으로 바꿔야 한다(식 형식·API는 그대로, 백엔드 내부만. 할 일 D-3).
- **평가 API** `POST /api/hmi/eval`: 식과 시험 값을 보내면 결과만 돌려준다(장비에 쓰지 않음, 저장하지 않음). 편집기 미리보기는 이것만 부른다 — 계산 구현은 백엔드 한 곳. 시험 값은 register 태그라도 **원본**으로 보낸다(프론트가 `WHMI.raw.toRaw`로 바꿈). 그래야 변환 함수까지 함께 시험된다.
- **쓰기 범위 검사**: `POST /api/hmi/write` 때 서버가 원본을 표시 값으로 바꿔 태그 `min`/`max`(비면 레지스터 범위)와 비교하고, 밖이면 422.

**프론트 런타임(구현됨, `js/whmi-runtime.js`)**

화면 로드 → 위젯 그리기 → 필요한 태그(위젯 `tag`·`writeTag`·조건 태그) 폴링(`pollMs`) → register 태그 원본을 표시 값으로 변환 → 상태 칸 3개 판정 → 위젯 갱신. 쓰기는 표시 값을 원본으로 역변환해 `POST /api/hmi/write {tag, raw}`.

**계산 위치를 백엔드로 정한 이유**: 브라우저에서 계산하면 창마다 따로 계산되고, 화면이 닫히면 계산이 멈추며, 트렌드·경보·상위 전송에 쓸 수 없다. 백엔드는 한 곳에서 계산해 모든 패널이 같은 값을 본다.

### 7.2 편집기 동작 요약

- 선택·이동·크기(여러 개 함께, 파워포인트 방식)·정렬·간격·순서, 격자 보기/맞춤, 실행 취소 50단계, 복사·붙여넣기(다른 화면에도).
- 속성 창: 위젯별 폼(그룹 접기, 기본값은 흐리게, 바꾼 것만 저장), 같은 종류 여러 위젯 동시 편집(일반 속성·색·동작 조건·목록형 속성. 태그와 이미지는 하나씩), "동작 조건" 그룹(조건 편집 부품 하나를 세 칸에 재사용).
- 색: 견본을 누르면 색 선택 창(색 판·색상 바·투명도 바·8자리 값·R G B A). 값 칸은 항상 `#RRGGBBAA`로 보이고 저장은 투명도 100%면 `#rrggbb`, 미만이면 `#rrggbbaa`. 목록 안의 색도 투명도를 줄 수 있고, 화면 배경색만 투명도가 없다. 숫자 칸은 포커스가 있을 때 마우스 휠로 바꾸면 바로 반영된다.
- 저장: 버튼·Ctrl+S, 256KB 사전 확인, 409 충돌 대화상자, 브라우저 임시 저장(다음 진입 때 복원 질문), 이탈 경고.
- 디자인 모드는 정지 화면: 열 때 읽은 값으로 한 번 그리고, 깜빡임 등 애니메이션은 멈춤. 숨김 조건이 거짓인 위젯은 흐리게.
- 바운딩 박스 규칙: 위젯 내용은 상자 밖으로 나갈 수 없음(`hmi-widgets.md` §4).

### 7.2.1 화면 이동 팝업 (실행 화면)

- 화면 이동 위젯의 `mode`: `replace`(화면 교체, 기본) / `modal`(팝업). 팝업용 화면 종류는 따로 없다 — 보통 화면을 작게 만들면 그것이 팝업 내용.
- 구현: `whmi-runtime.js`의 `nav.popup(screenId)`. 화면 영역 안에 `.whmi-pop-backdrop`을 띄우고 그 안에 `ScreenRuntime`을 하나 더 만든다(따로 폴링 — 본 화면도 계속 갱신). 위젯 id에 `pop-`를 붙여 그린다(clip·gradient id 겹침 방지).
- 크기: 본 화면과 같은 배율, 화면 영역의 94%를 넘으면 줄임. 제목 줄에 화면 제목과 ×.
- 닫기: ×, Esc(입력·확인 대화상자가 떠 있으면 그쪽이 먼저). 바깥을 눌러서는 닫히지 않는다. 본 화면이 바뀌거나 디자인 모드로 가면 함께 닫힌다.
- 한 번에 하나: 팝업 안에서 팝업을 열면 내용이 바뀌고, 화면 교체를 누르면 팝업을 닫고 본 화면을 바꾼다.

### 7.3 태그 관리

- 목록: TAG ID · TAG NAME · 종류(레지스터 / 로직) · 소스 · 단위 · 범위 · 스케일 · 권한 · 현재 값 · 사용처. **모든 칸은 한 줄**이고 넘치면 …로 줄인다(전체 내용은 마우스를 올리면). 소스는 레지스터 태그면 "장비 · 레지스터", 로직 태그면 식 글자(마우스를 올리면 입력 태그의 지금 값). 사용처는 "화면 N · 위젯 N · 식 N"(식 = 다른 태그의 식에서 참조). 상속 값은 흐리게, 검색·정렬.
- 만들기/수정: 장비 → 레지스터, 스케일(원본 기준, `현재 원본 2473 → 24.73` 미리보기), 단위·범위·권한(첫 항목 "레지스터 상속"). 여러 개 만들기·여러 개 삭제(사용처 확인 화면).
- 바로 열기: 속성 창의 태그·쓰기 태그 선택 옆 ⚙를 누르면 그 태그의 수정 폼으로 열리고(`open(editor, { editId })`), 저장·삭제·취소 뒤 목록 없이 편집기로 돌아온다. "+ 새 태그…"(`createFor`)와 같은 방식.
- **계산 태그(구현됨, `js/whmi-expr.js`)**: 새 태그 폼 맨 위의 종류 라디오(레지스터 / 로직 / 설정 — 설정은 준비 중이라 비활성)에서 고른다. 만든 뒤에는 종류를 바꿀 수 없다. 규칙 영역은 모든 조건 줄이 같은 칸 폭(장비 · 태그 · 비교 · 값)이고, 묶음 방식은 두 칸 버튼, 비트는 같은 폭 16칸이다. 미리보기는 식 · 결과 · 입력 값 표로 나뉜다.
  - 값 형식 참/거짓: "모두 만족(그리고) / 하나라도 만족(또는)" 묶음에 조건 줄을 넣는다. 묶음 안의 묶음까지(2단), 안쪽 묶음은 "반대로(아님)" 가능. 더 깊은 조합은 계산 태그를 이어 쓴다.
  - 값 형식 숫자·글자: "조건 → 값" 줄을 위에서부터 보고 처음 맞는 줄의 값, 없으면 "그 외에는" 값(`select`). 값 형식 숫자는 규칙 종류를 "조건 → 값 / 계산"에서 고른다 — 계산은 연산 하나 + 값 목록(태그 또는 숫자), "소수 자릿수" 칸은 `decimals`. 줄 하나에 조건을 여러 개 두고 "모두 만족 / 하나라도 만족"으로 묶을 수 있다(줄의 `+`, 1단·조건만 — 저장은 `select`의 조건 자리에 `and`·`or`).
  - 조건 줄: 장비 → 태그 → 비교(참일 때·거짓일 때·같음·다름·큼·크거나 같음·작음·작거나 같음·범위 안·비트) → 값. 참/거짓 계산 태그를 고르면 기본 비교는 "참일 때".
  - 미리보기: 조건을 바꾸면 0.5초 뒤 평가 API를 불러 식 글자·결과·품질·입력 태그 값을 보여 준다. "시험 값으로 보기"를 켜면 입력 값을 바꿔 볼 수 있다(장비에 쓰지 않음).
  - 빌더로 나타낼 수 없는 식(다른 태그와 비교, 3단 이상 묶음 등)은 식 글자만 보여 주고 저장해도 그대로 둔다.
- 계획(할 일 C·D): 설정 태그, 비교 대상에 다른 태그 넣기. 수식 글자 입력(수식 편집기)은 할 일 D — AST로 저장하므로 나중에 데이터 변경 없이 붙는다.

### 7.4 점검 규칙

| 등급 | 규칙 |
|---|---|
| 오류 | 소스 레지스터 없음 · 최소 ≥ 최대 · 화면이 정의 없는 태그를 참조(조건·쓰기 태그 포함) · 쓰기 위젯인데 읽기 전용 태그 · 화면 이동 대상 없음 · 조건 형식 오류·비트 미선택 · 쓸 값 미지정 |
| 경고 | 태그 단위 ≠ 레지스터 단위 · 현재 값이 범위 밖 · 통신 불량 · 값 위젯에 태그 없음 |
| 정보 | 사용 안 하는 태그 · 같은 레지스터를 쓰는 태그 · 소스 장비 비활성 |

규칙은 `TAG_RULES` / `WIDGET_RULES` 목록에 한 줄씩. 계산 태그가 생기면 "참조가 끊긴 계산 태그"(오류, 태그 응답의 `missingRefs`)를 더한다.

## 8. 저장 · 백업 · 이동

| 기능 | 동작 |
|---|---|
| 화면 저장 | 화면 단위. `PUT /api/hmi/screens/{id}` + revision(다르면 409, 저장한 사람·시각 포함). 제한: id `^[A-Za-z0-9_-]{1,64}$`, 제목 64자, 화면당 256KB, 최대 50개 |
| 태그 저장 | 바로 서버 반영(실행 취소 없음). 폴링 중에도 가능 |
| HMI 내보내기·불러오기 | 설정 → HMI 탭. `swr.hmi` 파일(프로젝트·화면·태그), 불러오기는 **전체 교체**, 재시작 없음, Manager 이상. 태그는 `unifiedAddress`로 레지스터를 다시 찾고 못 찾으면 건너뜀 |
| 시스템 백업·복원 | 백업 zip의 `hmi.json`에 HMI 포함(관리자, 재시작) |
| 공장 초기화 | HMI 프로젝트·화면·태그 모두 삭제 |
| 레지스터 삭제 | 그 레지스터의 register 태그도 함께 삭제. 화면에 남은 참조는 점검 "정의 없는 태그"로, expr 태그에 남은 참조는 `missingRefs`로 드러남(막지 않음) |
| 태그 직접 삭제 | expr 태그가 참조 중이면 409 + `referencedBy` 목록으로 거부(할 일 B) |
| 불러오기·복원과 expr 태그 | register → param → expr 순으로 넣음. 파일 안에 순환 참조가 있으면 **전체 거부**. 모르는 `kind`는 건너뛰고 경고. 내보내기 `schemaVersion`은 1 유지(예전 펌웨어는 expr·param 태그를 자동으로 건너뜀). param 태그는 현재 값도 함께 저장 |

**호환 규칙**

| 기존 | 처리 |
|---|---|
| `kind` 없는 태그 | `register` |
| 태그 `decimals`(2026-11-13 폐지) | 무시, 배율은 상속 |
| 위젯 `enableWhen: { tag, equals }` | `{ tag, test: "eq", value }`로 읽음, 편집기에서 저장하면 새 형식 |
| 램프 `bit`·`onValue`, 값 쓰기 버튼의 `onValue`(켜짐 표시 기준) | 실행 화면은 그대로 읽음. 속성 창에는 없고, 편집기가 화면을 열 때 같은 뜻의 `activeWhen`으로 바꿈(`migrate`, 2026-11-24) |
| 위젯 `props.unit`, 숫자 표시·입력의 `props.min`/`max` | 무시. 편집기가 열 때 지움(2026-11-24) |
| 위젯 `decimals`(2026-11-13 폐지) | 무시 |

## 9. 사용자 결정 사항

**구조**
- 프론트·백엔드 경계는 "값이 무엇인가 = 백엔드, 어떻게 보이나 = 프론트"(§4.1). 위젯 한 줄 조건은 프론트(B안), 쓰기 범위 검사는 백엔드에 요청.
- HMI 태그는 레지스터 `tagName`과 독립된 네임스페이스(레지스터 이름이 바뀌어도 화면은 깨지지 않음).
- 태그 4개 층 구조, kind 3종, AST 저장, 문자 ID, 값 타입 3종, 연결은 화면 문서 안(2026-11-24 설계 검토 수용).
- 계산은 백엔드, 미리보기도 백엔드 평가 API.
- 사건 기반 변수는 두지 않음. 설정값(param)은 둠.
- 태그 "값 형식"(비트·값 이름)은 HMI 태그에 정의(레지스터 `bitLabels` 입력은 2026-11-13 제거).

**화면·편집기**
- 화면 저장 단위는 화면별. 화면 크기는 디자인 기준 좌표계(실행 시 비율 유지 확대·축소). 크기를 바꿔도 위젯 좌표 유지.
- 그리는 순서는 자유. 격자 보기와 맞춤은 별도.
- 위젯 내용은 바운딩 박스 밖 불가. 실행 중 값 길이로 넘치는 것은 디자인으로 해결(자동 축소 없음).
- 속성 편집기는 전부 노출(그룹 접기). 여러 위젯 동시 편집은 같은 종류만.
- UI를 복잡하게 하는 보조 버튼은 넣지 않음.
- 장비 비활성은 통신 불량과 같게 표시.
- 태그 관리는 디자인 모드 안에. TAG ID는 만든 뒤 변경 불가.
- 점검은 버튼으로(단계 표시 0.35초), 저장·삭제 후엔 자동.
- 여러 개 삭제 기본은 "선택한 것 전부".
- 불러오기는 무조건 전체 교체(화면 단위 선택·병합 없음).
- 중복 정리(2026-11-24): 위젯의 단위 덮어쓰기와 숫자 표시·입력의 최소·최대 덮어쓰기 삭제, 램프·버튼의 켜짐 판정 칸을 켜짐 조건 하나로 통합, 설정 탭의 시작 화면 삭제. 램프 "알림창" 모양·막대 색 띠·스위치/전환 버튼·화면 이동 위젯은 그대로 둠.
- 개발 중 장비 데이터가 시험으로 바뀌어도 됨(무엇이 바뀌었는지만 보고).

## 10. 검토했지만 택하지 않은 안

| 안 | 택하지 않은 이유 |
|---|---|
| 태그에 통신 설정(장비·주소·기능 코드·데이터 형식) 두기 | 레지스터와 겹쳐 통신 정의가 두 곳이 됨. 폴링 묶음·백업이 두 갈래 |
| 정수 태그 ID + 바꿀 수 있는 이름 | 장비마다 ID가 달라 내보내기·복사·화면 JSON에서 충돌. 이름 바꾸기는 `name`으로 충분 |
| 데이터 타입 10종(Int16~Double) | 해석은 레지스터 일. 태그 값은 bool/number/string이면 충분 |
| 위젯 연결 DB 표(`widget_bindings`) | 화면 저장·충돌·불러오기·백업마다 표와 문서를 맞춰야 함. 사용처는 이미 편집기에서 계산 |
| 모든 속성 바인딩 | 바인딩 UI·타입이 위젯마다 필요. 상태 칸 + 정해진 모양 규칙으로 대부분 해결 |
| 조건 빌더와 수식 편집기 동시 제공 | 파서·오류 위치·왕복 보존 비용이 큼. AST 저장이라 나중에 붙일 수 있음 |
| 사건 기반 변수(Internal Tag의 할당형) | 사건을 놓치면 장비와 어긋남 |
| 위젯별 상태 태그 칸(전환 버튼에만) | 켜짐만 해결, 숨김·비활성으로 확장 안 됨 |
| 브라우저에서 계산 태그 계산 | 창마다 다른 값, 화면 닫히면 정지, 트렌드·경보에 못 씀 |

## 11. 테스트 방법

- **배포**: paramiko SFTP로 바뀐 파일만 `/var/www/html/`에 올린다(비밀번호는 환경 변수 `SWR_ROOT_PASS`, 저장소·스크립트에 쓰지 않음). `deploy.py`는 전체 배포 + 재부팅.
- **자동 시험**: Playwright(playwright-core + chromium)로 실제 장비에 로그인해 실행. 스크립트는 세션 임시 폴더에 둔다(재부팅 때 사라짐 — 필요하면 다시 작성).
- **회귀**: 시험 화면을 API로 만들고 값 응답을 가로채 고정 시나리오(값·품질)로 그린 스냅샷을 단계마다 비교. 끝나면 시험 화면·태그(`ZT_` 접두어) 삭제.
- **판정 엔진**: Node 단위 시험(장비 불필요). 계산 태그가 생기면 백엔드와 **공통 시험 데이터**(원본 → 표시 값, 식 → 결과)를 함께 쓴다.
- **필수 시험(계산 태그)**: 비트 0/15, AND/OR 중첩, 다른 태그와 비교, 이름 바꾼 뒤 참조 유지, 순환 참조 거부, 통신 불량 전파, 묶음 갱신 일관성, 저장·불러오기 왕복.
