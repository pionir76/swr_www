# HMI 동작 조건과 가상 태그 — 설계

> 작성: 2026-10-20 · **S1~S6 구현 완료: 2026-10-23** (가상 태그 S7은 미착수)
> 관련: `docs/architecture/hmi-builder.md`, `docs/reference/hmi-widgets.md`, `referencs/api-spec.md` §14

위젯의 상태(보이기, 조작 허용, 켜짐)를 **다른 태그의 값**에 따라 정하는 방법을 하나의 구조로 정리한다. 요구가 생길 때마다 위젯별로 칸을 덧붙이지 않기 위한 설계다.

---

## 1. 배경

- TP2KMF는 **명령 레지스터(OPMODE)**와 **상태 레지스터(NOW_STS)**가 따로 있다. OPMODE는 1(운전)·4(정지)를 쓰면 바로 0으로 돌아가므로 읽어서는 운전 여부를 알 수 없다.
- 그래서 OPMODE에 쓰는 전환 버튼은 늘 "꺼짐"으로 판단해 1만 쓴다. 켜짐 여부는 NOW_STS(비트 1·2)에서 읽어야 한다.
- 비슷한 요구가 이어질 수 있다: 다른 태그 값에 따라 위젯을 숨기기, 조작을 막기, 켜짐으로 보이기.

## 2. 현재 구조와 문제

위젯 데이터: `{ id, type, x, y, w, h, tag, props, enableWhen }`

| 조건 처리 | 판정 대상 | 표현 | 위치 |
|---|---|---|---|
| 값 표시·쓰기 | 자기 태그(`tag`) | — | 공통 |
| 조작 허용 | 다른 태그 가능 | `{ tag, equals }` 같음만 | `enableWhen` |
| 램프 켜짐 | 자기 태그 | `onValue` / `bit` | 램프 props |
| 버튼 켜짐 표시·전환 판단 | 자기 태그 | `onValue` | 버튼 props |
| 스위치 켜짐 | 자기 태그 | `onValue` / `offValue` | 스위치 props |
| 상태 표시 | 자기 태그 | 값 일치 / 비트 목록 | 상태 표시 props |
| 구간 색·깜빡임 | 자기 값 | `ranges` | 값 위젯 props |
| 보이기 / 숨기기 | — | 없음 | — |

문제:

1. 조건 표현이 위젯마다 제각각이다(같음, 비트, 범위가 서로 다른 속성 이름과 UI).
2. `tag` 하나가 **쓰기 대상과 상태 판정을 겸한다.** 둘이 다른 레지스터면 표현할 수 없다.
3. 다른 태그를 보는 조건은 `enableWhen` 하나뿐이고 같음 비교만 된다.

## 3. 설계

### 3.1 조건(Condition) — 하나의 표준 형식

```json
{ "tag": "TP2KMF_NOWSTS", "test": "bitAny", "bits": [1, 2] }
{ "tag": "RUN_REG",       "test": "eq",     "value": 1 }
{ "tag": "PRESSURE",      "test": "gt",     "value": 12.5 }
```

| test | 참이 되는 때 | 추가 필드 |
|---|---|---|
| `eq` / `ne` | 값이 같음 / 다름(숫자·참거짓·문자, 느슨한 비교) | `value` |
| `gt` / `lt` | 값이 큼 / 작음 | `value` |
| `bitAny` | 고른 비트 중 하나라도 1 | `bits` (0~15) |
| `bitNone` | 고른 비트가 모두 0 | `bits` |

- 태그 값이 통신 불량(`q: bad`)이면 조건은 **판정 불가**다. 칸마다 처리는 3.2 표를 따른다.
- 조건 하나는 "태그 하나 + 비교 하나"로만 쓴다. 조합(그리고/또는)은 가상 태그(4장)로 만든다.

### 3.2 위젯 상태 칸 3개

모든 위젯에 같은 이름, 같은 뜻으로 둔다. 위젯 필드(`props` 밖, 지금의 `enableWhen`과 같은 위치).

| 칸 | 질문 | 조건 거짓 | 판정 불가(통신 불량) | 비워 두면 |
|---|---|---|---|---|
| `visibleWhen` 보이기 | 언제 보이나? | 숨김 | 보임(안전 쪽: 정보를 감추지 않음) | 항상 보임 |
| `enableWhen` 조작 허용 | 언제 누를 수 있나? | 흐리게, 클릭 막음 | 막음 | 항상 허용 |
| `activeWhen` 켜짐 상태 | 언제 "켜짐"으로 보나? | 꺼짐 모습 | 꺼짐 모습 | 지금처럼 자기 태그로(켜짐 값 / 비트) |

- `tag`는 **값 표시와 쓰기 대상**으로만 쓴다. 상태는 언제나 이 3칸이 정한다.
- 자기 값에 따른 모양(구간 색, 상태 표시 목록, 게이지 바늘)은 지금처럼 위젯 props에 둔다.

OPMODE / NOW_STS 사례:

```json
{ "type": "button", "tag": "TP2KMF_OPMODE",
  "props": { "action": "toggle", "onValue": 1, "offValue": 4 },
  "activeWhen": { "tag": "TP2KMF_NOWSTS", "test": "bitAny", "bits": [1, 2] } }
```

버튼은 OPMODE에 쓰고, 켜짐 여부(전환 판단, 켜짐 글자·색)는 NOW_STS로 정한다.

### 3.3 판정은 런타임 한 곳에서

- 런타임(`whmi-runtime.js`)이 매 폴링마다 3칸을 판정해 위젯에 `info.visible / info.enabled / info.active`로 넘긴다.
- 위젯은 조건을 직접 해석하지 않는다.
  - 숨기기·조작 막기: 런타임이 모든 위젯에 공통 적용(숨김 클래스, `readonly`)
  - 켜짐: 위젯별 모습(램프 점등, 버튼 색·글자와 전환 판단, 스위치 위치)
- 조건에 나온 태그는 런타임이 자동으로 함께 폴링한다(지금 `enableWhen`의 추가 폴링을 일반화).
- 디자인 모드는 정지 화면 원칙 그대로: 미리보기는 열 때 읽은 값으로 한 번 판정, 숨김 위젯은 편집기에서 흐리게 보이게(선택·편집은 가능).

### 3.4 편집기

조건 편집 부품 하나를 세 칸에 재사용한다.

```
▼ 동작 조건                       (기본 접힘)
  보이기      [항상 ▾]
  조작 허용   [조건 지정 ▾] [장비 ▾][태그 ▾] [같음 ▾] [1]
  켜짐 상태   [조건 지정 ▾] [장비 ▾][태그 ▾] [비트 중 하나라도 1 ▾] 0 [1][2] 3 … 15
```

- 장비 → 태그 선택, 비트 격자 등 이미 있는 부품을 조합한다.
- 비교 방식에 따라 값 칸 / 비트 격자가 바뀐다.
- 켜짐 상태 칸은 켜짐이 있는 위젯(램프, 버튼, 스위치)에만 보인다.
- 태그 점검: 조건의 태그가 정의되지 않음(오류), 비트 비교인데 비트를 고르지 않음(오류).

### 3.5 기존 데이터와의 호환

| 기존 | 처리 |
|---|---|
| `enableWhen: { tag, equals }` | 읽을 때 `{ tag, test: "eq", value: equals }`로 해석. 편집기에서 저장하면 새 형식 |
| 램프 `onValue`/`bit`, 버튼·스위치 `onValue` | `activeWhen`을 비워 두면 지금처럼 동작 → 기존 화면 변경 없음 |
| 화면 JSON | 새 필드 `visibleWhen`, `activeWhen`만 추가. 백엔드는 화면 내용을 그대로 저장하므로 **백엔드 변경 없음** |

## 4. 가상 태그

### 4.1 개념

태그 관리에서 일반 태그처럼 만들고, 소스로 장비 대신 **"가상 태그"**를 고른다. 값은 **다른 태그에서 매번 계산**된다. 위젯 조건과 상태 칸에서는 일반 태그와 똑같이 고른다.

| 유형 | 값 형식 | 계산 | 예 |
|---|---|---|---|
| 판정형 | 참/거짓 | 조건 목록을 "모두" 또는 "하나라도"로 묶음 | `RUNNING`(운전중) = NOW_STS 비트 1·2 중 하나라도 1 / `CAN_START`(기동 가능) = RUNNING이 거짓 **그리고** ALSTS = 0 |
| 선택형 | 숫자·문자 | 조건 목록에서 처음 맞는 줄의 값, 없으면 기본값 | `MODE_TEXT` = 비트 2면 "PROG", 비트 1이면 "FIX", 아니면 "STOP" |

- 가상 태그는 다른 가상 태그를 조건에 쓸 수 있다(이어 쓰기). **순환 참조는 금지**(저장 시 거부).
- 입력 태그 중 하나라도 통신 불량이면 가상 태그도 불량(`q: bad`).
- 가상 태그는 읽기 전용이다(쓰기 위젯의 쓰기 대상으로는 못 고름).

### 4.2 넣지 않는 것: 기억형(사건 기반) 변수

"태그 X가 바뀌면 변수에 값을 넣는다"처럼 **사건이 생길 때만 바뀌고 값을 기억하는** 변수는 넣지 않는다.

- 사건을 놓치면(현장 조작반 조작, 통신 단절, 백엔드 재시작) 실제 장비와 값이 어긋난다.
- OPMODE처럼 변화가 보이지 않는 레지스터에는 쓸 수 없다.
- 계산형은 항상 실제 값에서 다시 계산하므로 어긋나지 않는다.

### 4.3 계산 위치: 백엔드

| 계산 위치 | 결과 |
|---|---|
| 브라우저 | 창마다 따로 계산, 화면이 닫혀 있으면 계산 안 됨, 트렌드·상위 전송에 못 씀 |
| **백엔드(채택)** | 한 곳에서 계산해 `/api/hmi/values`로 일반 태그처럼 제공. 모든 패널이 같은 값 |

백엔드가 맡을 일(요청서 필요):

- 가상 태그 정의 저장(`/api/hmi/tags`에 소스 종류 추가) + 백업·복원
- 폴링마다 계산: 의존 순서 정리, 순환 참조 거부, 품질 전파
- 값 응답은 일반 태그와 같은 형식(`v`, `q`)

### 4.4 태그 관리 화면

```
새 태그 정보
 소스      [가상 태그 ▾]          ← 장비 목록 맨 위
 TAG ID    [RUNNING]   TAG NAME [운전중]
 값 형식   [참/거짓 ▾]
 규칙      [모두 ▾ 만족하면 참]
           [장비 ▾][태그 ▾][비교 ▾][값 / 비트 격자]   ×
           + 조건 추가
```

- 조건 줄은 위젯 상태 칸과 **같은 조건 편집 부품**을 쓴다.
- 목록에서 소스는 "가상", 현재 값은 일반 태그처럼 표시. 이어 쓴 가상 태그를 추적할 수 있게 입력 태그의 현재 값도 함께 보여 준다.

## 5. 원칙

- 위젯 조건은 **태그 하나 + 비교 하나**. 복잡한 판단은 가상 태그에 **이름을 붙여** 모은다.
- 스크립트·수식은 넣지 않는다(화면 설정이 프로그래밍이 되지 않게).
- 가상 태그는 **계산형만**(판정형·선택형). 기억형은 넣지 않는다.
- **안전 인터록이 아니다.** 조작 허용 조건은 화면 편의일 뿐이며, 실제 보호 로직은 PLC·제어기에 있어야 한다. 편집기 도움말에도 명시한다.

## 6. 진행 단계

| 단계 | 내용 | 담당 |
|---|---|---|
| 1 | 조건 형식 + 상태 칸 3개, 런타임 판정 일원화, 기존 `enableWhen` 호환 | 프론트 |
| 2 | 조건 편집 부품 + "동작 조건" 그룹, 램프·버튼·스위치 켜짐 연동, 점검 규칙, 회귀 테스트 | 프론트 |
| 3 | 가상 태그 정의·계산·값 제공 | 백엔드(요청서) |
| 4 | 태그 관리에 "가상 태그" 소스 + 규칙 편집 | 프론트 |

1~2단계만으로 OPMODE / NOW_STS 문제와 숨김·비활성 요구가 해결된다. 3~4단계는 조합 판단이 필요해질 때 진행한다.

## 6-1. 보강(2026-10-23): 판정 엔진 일원화

업계 제품 조사(WinCC·FactoryTalk·InTouch·CODESYS·Pro-face = 상태 칸 + 조건, Ignition = 속성 바인딩 + Map 변환 + 수식 태그) 결과, 위 설계(상태 칸 + 계산 태그)는 주류 방식과 같다. 여기에 **판정 엔진 하나**를 더한다.

- 지금 위젯마다 따로 있는 "값 → 결과" 규칙(램프 `onValue`/`bit`, `enableWhen`, 상태 표시 `states`, 구간 색 `ranges`, 버튼 `onValue`)을 **같은 엔진**(`js/whmi-rules.js`)이 판정한다.
- 엔진은 **조건**(eq·ne·gt·lt·range·bitAny·bitNone)과 **대응표**(위에서부터 처음 맞는 줄)만 안다. 형 변환·비트·통신 불량 처리를 한 곳에서 같은 규칙으로.
- 판정 불가(값 없음·`bad`·`disabled`)는 `null`로 돌려주고, 쓰는 쪽(칸·위젯)이 정해진 기본 결과를 쓴다(3.2 표).
- 바인딩 가능한 것은 상태 칸 3개와 위젯별로 정해진 모양 규칙으로 한정한다(모든 속성 바인딩은 하지 않음).

### 엔진 규칙

| 항목 | 규칙 |
|---|---|
| 같음(eq/ne) | 두 값이 모두 숫자로 읽히면(참/거짓은 1/0) 숫자 비교, 아니면 글자 비교 |
| 큼·작음(gt/lt) | 숫자로 읽힐 때만. 아니면 거짓 |
| 범위(range) | `min ≤ 값 ≤ max`(양 끝 포함, 비우면 끝없음) — 기존 구간 색과 같음 |
| 비트(bitAny/bitNone) | 값을 정수로 내림해 비트 판정(0~31). 비트를 안 고르면 거짓 |
| 판정 불가 | 값이 없거나 품질 `bad`/`disabled` → `null`. `normal`은 값이 있으므로 판정 |
| 대응표 | 위에서부터 처음 맞는 줄. 맞는 줄이 없으면 "없음", 판정 불가면 `null` |

## 6-2. 구현 계획(단계별 테스트)

| 단계 | 내용 | 테스트 |
|---|---|---|
| S1 | 판정 엔진 `js/whmi-rules.js` + 실행 화면·편집기에서 로드. 기존 화면 기준 스냅샷 저장 | 엔진 단위 테스트(Node, 장비 불필요). 기준 스냅샷: main·chiller 실행 화면을 **고정 값**(값 응답 가로채기)으로 그려 위젯별 모습 기록 |
| S2 | 런타임이 **모든 위젯**(태그 없는 위젯 포함) 관리, 상태 칸 3개(`visibleWhen`/`enableWhen`/`activeWhen`) 판정, 조건 태그 자동 폴링, 기존 `enableWhen` 호환 | 시험 화면(API로 생성 후 삭제)에서 값을 바꿔 가며 숨김·조작 막기·켜짐 확인. 기존 화면 스냅샷 비교(변화 없어야 함) |
| S3 | 램프·버튼·스위치가 `activeWhen` 결과 사용, 전환 버튼은 켜짐이면 꺼짐 값 | OPMODE/NOW_STS 형태 시험(쓰기 요청은 가로채서 값만 확인) |
| S4 | 기존 규칙(램프 비트·켜짐 값, 상태 목록, 구간 색)을 내부적으로 엔진으로 이전(저장 형식 그대로) | 스냅샷 비교 + 경계값(구간 끝, 비트, 품질 불량) 시험 |

## 7. 검토했지만 택하지 않은 안

| 안 | 내용 | 택하지 않은 이유 |
|---|---|---|
| 위젯별 상태 태그 칸 | 전환 버튼·스위치에만 "상태 태그 + 비트" 추가 | 켜짐 판정만 해결, 숨김·비활성 등으로 확장 안 됨(땜질) |
| 사건 기반 HMI 변수 | 태그 변화에 따라 변수에 값 할당, 위젯이 변수를 읽음 | 실제 장비와 어긋날 위험, 브라우저 계산 시 일관성 없음 |
