# HMI 태그 구조 — 설계 합의서

> 작성: 2026-11-24 (프론트엔드)
> 대상: SmartRoute 백엔드(swr)
> 설계 문서: `docs/architecture/hmi.md` (이 문서의 "§"는 그 문서의 절 번호)
> 할 일: `docs/architecture/hmi-todo.md` 단계 A

---

## 1. 이 문서의 목적

**지금 구현을 요청하는 문서가 아닙니다.** HMI 태그의 자료구조를 앞으로 어떻게 넓힐지 먼저 합의하려는 문서입니다. 합의가 끝나면 단계별 구현 요청서(첫 번째는 계산 태그)를 따로 보냅니다.

타 팀 설계안 "SWR HMI Tag Engine"(Direct / Derived / Internal 태그, 식 AST, 태그 엔진)을 지금 구조와 맞대어 검토했고, 사용자가 아래 방향을 확정했습니다.

- 구조는 4개 층으로 나눕니다: **레지스터(통신) → HMI 태그(의미·계산) → 엔진(계산·판정) → 화면·위젯(표시)** (§2).
- 한 정보는 한 곳에만 정의합니다. 통신 설정은 레지스터에만, 계산 식은 태그에만 둡니다.
- 식은 정해진 연산자만 쓰고(스크립트 없음), 데이터(JSON AST)로 저장합니다.

- 프론트와 백엔드의 경계는 **"태그 값이 무엇인가는 백엔드, 그 값을 어떻게 보이나는 프론트"**입니다(§4.1). 태그 사이의 계산·조합과 쓰기 검증은 백엔드, 소수점·단위·색·보이기 같은 표시는 프론트가 맡습니다. 위젯의 한 줄 조건(태그 하나 + 비교 하나로 모양을 정함)은 표시로 보고 프론트에 둡니다.

합의할 것은 2장의 7가지이고, 백엔드 의견이 필요한 질문은 3장에 모았습니다.

---

## 2. 합의할 내용

### 2.1 태그 종류 필드 `kind`

HMI 태그에 `kind`를 둡니다. 값이 없으면 `register`로 읽어 지금 데이터가 그대로 동작합니다.

| kind | 뜻 | `source` | 값 | 쓰기 |
|---|---|---|---|---|
| `register` | 레지스터 하나를 가리키는 태그(지금의 모든 태그) | `{ "registerId": 12 }` | 원본 `raw` | `access: rw`면 원본으로 |
| `expr` | 다른 태그로 계산하는 태그 | `{ "valueType": "bool", "expr": { AST } }` | 계산한 `value` | 불가 |
| `param` | 사용자가 HMI에서 바꾸는 설정값 | `{ "valueType": "number", "initial": 80 }` | 저장된 `value` | 사용자 쓰기로만 |

- **태그에 통신 설정(장비·주소·기능 코드·데이터 형식·바이트 순서)은 두지 않습니다.** 설계안의 Direct Tag는 이 정보를 갖지만, 레지스터 정의와 겹치므로 지금처럼 `registerId` 참조만 씁니다.
- 태그 ID는 지금처럼 **문자, 만든 뒤 변경 불가**입니다. 정수 ID는 쓰지 않습니다(장비 간 복사·내보내기 파일·화면 JSON에서 충돌). 이름 바꾸기는 `name`으로 받습니다.
- 값 타입(`valueType`)은 `bool` / `number` / `string` 3종입니다. 정수 폭·실수 형식은 레지스터 해석 단계의 일로 봅니다.
- `param`은 "X가 바뀌면 Y에 값을 넣는" 사건 기반 변수가 아닙니다. 사용자가 직접 쓸 때만 바뀌는 저장 값입니다.

### 2.2 식(AST) 형식

노드는 세 가지입니다(§5.3).

```json
{ "tag": "NOW_STS" }                 // 태그 참조(문자 ID)
{ "value": 3 }                       // 상수(숫자·문자·참거짓·비트 목록)
{ "op": "and", "args": [ ... ] }     // 연산
```

예: `NOW_STS 비트 1·2 중 하나라도 1` 그리고 `ALSTS = 0`

```json
{ "op": "and", "args": [
  { "op": "bitAny", "args": [ { "tag": "NOW_STS" }, { "value": [1, 2] } ] },
  { "op": "eq",     "args": [ { "tag": "ALSTS" },   { "value": 0 } ] } ] }
```

연산자 이름과 단계:

| 묶음 | 연산자 | 결과 | 단계 |
|---|---|---|---|
| 비교 | `eq` `ne` `gt` `ge` `lt` `le` `range` | bool | B |
| 비트 | `bitAny` `bitNone` (비트 0~15, 정수에만) | bool | B |
| 논리 | `and` `or` `not` (중첩 가능) | bool | B |
| 선택 | `select` — `[조건, 값, 조건, 값, …, 기본값]` 처음 맞는 값 | 값 | B |
| 산술 | `add` `sub` `mul` `div` `min` `max` `avg` `abs` | number | C |
| 시간·상태 | `hysteresis` `ton` `tof` `rising` `latch` | bool | D |

- 비교·비트 이름은 프론트 판정 엔진(`js/whmi-rules.js`)이 이미 쓰는 이름과 같습니다. 비교 규칙(숫자로 읽히면 숫자 비교, 참/거짓은 1/0, 범위는 양 끝 포함)도 §5.6과 같게 맞추면 화면 조건과 계산 태그의 결과가 어긋나지 않습니다.
- 연산자마다 인수 개수·입력 타입·결과 타입·계산 함수를 한 줄로 정의하는 **등록부** 방식을 권합니다. 연산자를 추가할 때 등록부에 한 줄만 더하면 됩니다.
- 저장할 때 거부할 것: 인수 개수·타입 불일치, 없는 태그 참조, 순환 참조, 비트 범위 밖.

### 2.3 표시 값 변환과 원본 데이터 원칙

계산 태그는 `TEMP >= 80`처럼 **배율을 적용한 값**으로 비교해야 하므로, 원본 데이터 원칙에 다음 문구를 보강했습니다(`docs/architecture/overview.md` §5.1).

- 통신 원본의 저장·전송은 **계속 원본 그대로**입니다. register 태그 값, 실시간, 트렌드, Modbus 서버는 바뀌지 않습니다.
- 원본 → 표시 값 변환(부호 해석 × 배율, 나중에 + 오프셋)은 태그 설정으로 정해지는 **하나의 함수**입니다. 계산 엔진은 식을 평가할 때 이 함수를 씁니다.
- 프론트(`WHMI.raw`)와 백엔드 구현이 같은 결과를 내도록 **공통 시험 데이터**(2.6)로 함께 검증합니다.

### 2.4 값 응답 형식

`GET /api/hmi/values`에서 kind에 따라 필드가 다릅니다.

```json
{ "TK1_LEVEL": { "raw": 569, "q": "good", "unit": "%", "access": "r" },
  "RUNNING":   { "value": true, "q": "good" } }
```

- register 태그: 지금 그대로 `raw`.
- expr·param 태그: 원본이 아니므로 `value`.

### 2.5 계산 엔진과 품질 전파

- 태그 저장 때 의존 그래프를 만들고 순환 참조를 거부합니다.
- 폴링 묶음이 끝난 뒤, 영향받은 expr 태그를 의존 순서대로 한 번씩 계산합니다(같은 묶음에서 중복 계산 없음).
- 품질: 입력 중 하나라도 `bad`/`disabled`이면 결과도 `bad`, `normal`이 섞이면 `normal`. 마지막 정상값을 들고 있지 않습니다.
- 평가 중 0으로 나누기 같은 오류는 판정 불가(`bad`)로 처리합니다.

### 2.6 평가 API와 공통 시험 데이터

- **평가 API:** 식과 시험 값을 보내면 결과만 돌려주는 API를 둡니다(장비에 쓰지 않음, 저장하지 않음). 편집기의 미리보기는 이것만 부릅니다. 계산 구현을 백엔드 한 곳에만 두기 위해서입니다.
  ```json
  // 요청 예
  { "expr": { AST }, "valueType": "bool",
    "inputs": { "NOW_STS": 6, "ALSTS": 0 } }      // 생략한 태그는 현재 값
  // 응답 예
  { "value": true, "q": "good", "inputs": { "NOW_STS": { "value": 6, "q": "good" } } }
  ```
- **공통 시험 데이터:** JSON 파일 두 개를 저장소에 두고 양쪽 단위 시험이 함께 읽습니다.
  - 변환 표: `{ raw, isSigned, scale } → 기대 표시 값`
  - 식 표: `{ expr, inputs } → 기대 value·q`

  파일 위치는 `referencs/`를 제안합니다(초안은 프론트가 작성).

### 2.7 하지 않기로 한 것

| 설계안 항목 | 결정 | 이유 |
|---|---|---|
| 위젯 연결 DB 표(`widget_bindings`) | 만들지 않음 | 연결은 화면 문서(JSON) 안에 있습니다. 화면 저장·충돌 확인·불러오기·백업마다 표와 문서를 맞추는 비용이 큽니다 |
| 수식 글자 입력(Expression Editor) | 뒤로 미룸(단계 D) | 저장 원본이 AST라 나중에 데이터 변경 없이 붙일 수 있습니다. 먼저 조건 빌더만 만듭니다 |
| 시간·상태 연산 | 뒤로 미룸(단계 D) | 노드별 상태·타이머·재시작 정책이 필요합니다 |
| 사건 기반 변수 | 하지 않음 | 사건을 놓치면 장비와 어긋납니다 |

## 3. 백엔드 의견이 필요한 질문

1. **참조 중인 태그 삭제.** expr 태그가 참조하는 태그를 지울 때 거부(409 + 참조하는 태그 목록)할지, 지우고 expr 태그를 판정 불가로 둘지. 프론트는 **거부**를 제안합니다. 다만 레지스터 삭제 → register 태그 연쇄 삭제가 지금 있으므로, 이 경우를 어떻게 맞출지 의견 부탁드립니다.
2. **계산 시점과 부하.** 폴링 묶음마다 계산할지, 입력이 바뀔 때만 계산할지. 태그 수·식 깊이에 한도가 필요한지(i.MX6ULL 기준).
3. **표시 값 변환의 기준.** 2.3의 함수를 백엔드에 두는 데 문제가 없는지. 예전에 `scaledValue`를 만들던 코드와의 관계(되살리는 것이 아니라 계산 엔진 안에서만 쓰는 함수로 생각합니다).
4. **쓰기 범위 검사.** 지금 서버는 태그 `min`/`max`로 쓰기를 검사하지 않고, 프론트 입력 창만 검사합니다. API를 직접 부르면 범위 밖 값도 써집니다. 2.3의 변환 함수가 백엔드에 생기면 `POST /api/hmi/write` 때 서버가 태그 범위(비면 레지스터 범위)를 검사해 422로 거부하는 것을 제안합니다. 프론트 검사는 편의용으로 남깁니다. 참고로 위젯의 "조작 허용 조건"은 화면 편의로만 두며 서버 강제를 요청하지 않습니다.
5. **여러 워드 레지스터.** HMI 태그는 지금 1워드만 받습니다. 나중에 `values`에 `rawWords`(실시간 API와 같은 형식)를 주는 방식이면 프론트는 기존 해석 코드를 그대로 씁니다. 이 방향에 문제가 없는지.
6. **내보내기 파일 버전.** `kind`가 추가될 때 `swr.hmi`의 `schemaVersion`을 올릴지. 예전 파일은 kind 없음 = register로 읽히므로 올리지 않아도 된다고 봅니다. 반대로 새 파일을 예전 펌웨어가 읽을 때의 처리(모르는 kind는 건너뜀?)는 정해야 합니다.
7. **현재 DB 구조와의 차이.** 위 구조를 넣을 때 태그 테이블 변경 범위(컬럼 추가인지, `source`를 JSON으로 바꾸는지)와 마이그레이션 부담.
8. **그 밖에** 백엔드 내부 구조(폴링 캐시, 스레드)와 충돌하는 부분이 있으면 알려 주세요. 프론트는 API 명세만 보고 판단했습니다.
