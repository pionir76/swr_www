## 2. 요청서에 없던 세부 / 다르게 정한 것

### 2.1 태그 API

1. **PUT에서 `kind`를 생략하면 지금 종류를 유지합니다.**
   - 요청서는 "없으면 `register`"였습니다. 그대로 두면 계산 태그를 `kind` 없이 PUT할 때 "종류 변경" 400이 됩니다.
   - POST에서는 요청서대로 `register`입니다.
   - `kind`를 보냈는데 지금 종류와 다르면 400입니다.
2. **`kind: "param"`은 아직 400입니다**(`'kind' must be "register" or "expr"`).
3. **422 `path`:**
   - 맨 위 노드가 문제면 `""`입니다. 순환 참조·깊이 초과처럼 특정 노드가 아닌 문제도 `""`입니다.
   - 없는 태그 참조는 그 태그를 처음 참조한 노드를 가리킵니다.
4. **태그 수 초과**(1,000개)는 422 `{ "error": ..., "maxTags": 1000 }`이고 `path`가 없습니다.
5. **노드의 다른 키는 무시합니다.** `{ "tag": "A", "note": "…" }`처럼 편집기용 키를 붙여도 저장됩니다.
6. **상수:** 숫자·글자·true/false·`null`입니다. 배열은 `bitAny`/`bitNone`의 두 번째 인수(비트 목록) 자리에만 둘 수 있고, 다른 자리는 422입니다.
   - 비트 목록은 `{ "value": [...] }` 상수여야 합니다. 태그를 넣으면 422입니다.
   - 빈 목록 `[]`은 허용하며 결과는 거짓입니다.

### 2.2 계산 규칙

1. **`valueType: "number"`인데 결과가 숫자로 읽히지 않으면 `bad`입니다.** 예: `select`가 글자 `"RUN"`을 돌려줄 때.
2. **`valueType: "string"`은 JavaScript `String()`과 같은 글자로 바꿉니다.** 예: `247.5` → `"247.5"`, `true` → `"true"`.
3. **숫자로 읽기의 작은 차이:** 서버는 `"0x1F"`(16진수) 모양의 글자를 숫자로 읽지 않습니다. JavaScript `Number()`는 읽습니다.
   - 글자 상수를 16진수로 쓰지 않는 한 결과는 같습니다.
   - 시험 데이터에는 이런 경우가 없습니다.
4. **`bitAny`/`bitNone`:** 값을 0 쪽으로 자른 정수의 32비트로 봅니다. 프론트 `Math.trunc` + `>>`와 같습니다.

### 2.3 `GET /api/hmi/values`

- 계산 태그의 `unit`은 태그 값이고, 없으면 `""`입니다. `access`는 항상 `"r"`입니다.
- 계산 태그를 요청하면 그 태그가 참조하는 태그만 계산합니다. 응답에는 **요청한 태그만** 나옵니다.

### 2.4 `POST /api/hmi/eval`

1. **없는 태그 참조는 422가 아닙니다.** 결과 `bad`에 `missingRefs`(최상위 필드)로 알려 줍니다.
   - 편집기가 저장 전에 같은 판단을 하려면 `missingRefs`가 비었는지 보면 됩니다.
   - 저장(POST/PUT)에서는 요청서대로 422입니다.
2. **`inputs`로 값을 준 계산 태그는 그 아래를 계산하지 않습니다.** 그래서 응답 `inputs`에 그 아래 태그는 나오지 않습니다.
3. `inputs`의 계산 태그에 `"value": null`을 주면 `q`와 관계없이 `bad`입니다.
4. 이 장치에 없는 태그 id를 `inputs`에 주면 무시합니다(400 아님).
5. register 태그 입력의 `raw`가 정수 0–65535나 `null`이 아니면 400입니다. `q`가 `good`/`normal`/`bad`/`disabled`가 아니어도 400입니다.

### 2.5 쓰기 범위 검사

- 422 본문의 `min`/`max`는 실제로 비교한 값입니다(물려받았으면 환산한 값). 제한이 없는 쪽은 `null`입니다.
- `value`는 `raw`를 바꾼 표시 값입니다.
- 계산 태그에 쓰면 **405**입니다(읽기 전용 태그와 같음).

### 2.6 불러오기 검증 응답 (요청서 2.7에서 이름을 맡긴 필드)

```json
"tags": { "total": 9, "linked": 6, "missing": [],
          "expr": 3, "brokenExpr": [ { "id": "RUNNING", "missingRefs": ["NOW_STS"] } ] }
```

- `expr`: 파일의 계산 태그 수입니다.
- `brokenExpr`: 적용 뒤 참조가 끊길 계산 태그입니다. 건너뛸 register 태그나 파일에 없는 태그를 참조하는 경우입니다. 이 태그들도 들어가고 값은 `bad`입니다.
- **`linked`는 이제 register 태그만 셉니다.** 예전에는 `total - missing`이었습니다. 화면이 "연결 n / 전체 m"을 보여 주고 있다면, 이제 `linked + missing.length = register 태그 수`입니다.
- 모르는 `kind`(예: `param`)는 `warnings`에 나오고 적용 때 건너뜁니다.
- 적용 응답에도 `warnings`를 더했습니다. 응답의 `tags`는 실제로 들어간 태그 수입니다.

### 2.7 시스템 복원

- "장비만 복원, HMI 유지"이면 계산 태그는 그대로 남습니다. register 태그는 지금처럼 다시 연결합니다. 참조가 끊긴 계산 태그는 복원 경고에 나옵니다.
- 백업 파일 안의 계산 태그가 잘못되었거나 순환하면, **복원은 계속하고** 그 태그만 건너뛴 뒤 경고합니다.
  - HMI 불러오기 API는 이런 파일을 400으로 전체 거부합니다.
  - 시스템 복원은 설정·장비까지 함께 바뀌므로 HMI 때문에 전체를 멈추지 않게 했습니다.

### 2.8 부하 (답변서 질문 2의 "태그 캐시")

- 태그 목록 전체를 메모리에 두는 캐시는 **만들지 않았습니다.**
  - 레지스터·장비 삭제, 복원, 불러오기, 공장 초기화가 모두 태그를 바꿉니다. 이 경로마다 캐시를 비우는 비용과 위험이 이득보다 큽니다.
  - 대신 **식 해석 결과만 캐시**합니다. 저장된 식 글자가 키라서, 식을 바꾸면 자동으로 새로 해석합니다.
- 장치 실측:

| 요청 | 시간 |
|---|---|
| `values?tags=` 3개(화면 런타임 방식) | 약 20ms |
| `values` 전체, 태그 9개(계산 3) | 약 13ms |
| `values` 전체, 태그 109개(계산 103, 노드 14개씩) | 약 66ms |
| `GET /api/hmi/tags`, 태그 109개 | 약 160ms |

- 화면 런타임은 화면에서 쓰는 태그만 요청하므로 문제가 없습니다.
- 태그 관리 화면처럼 `values`를 전체로 부르는 곳은 계산 태그가 수백 개가 되면 수백 ms가 걸릴 수 있습니다. 필요하면 보이는 태그만 요청해 주세요.

  - 계산 태그 생성 3건

  - `kind` 변경 400, `param` 400
  - 참조 중인 태그 삭제 409
- **`values`:** `RUNNING`(NOW_STS 비트 0) → `true`, `CAN_START` → `false`, `STATE_TXT`(select) → `"RUN"`
- **`eval`:**
  - 입력 덮어쓰기(register `raw`, 계산 태그 `value`)
  - 부호 있는 음수 + `normal` 품질
  - 없는 태그 → `bad` + `missingRefs`
  - 인수 개수 422
- **쓰기:**
  - 태그 범위(1–10) 밖 11·0 → 422
  - 레지스터 범위를 물려받은 0–16 밖 17 → 422
  - 범위 안 0 → 202(지금 값과 같은 값이라 장비 상태는 그대로)
  - 계산 태그 쓰기 → 405
- **내보내기·불러오기:**
  - 계산 태그가 포함됩니다.
  - 검증: `brokenExpr`, 순환 파일 400, 모르는 `kind` 경고
  - 참조가 끊기는 파일을 적용하면 해당 태그가 `bad` + `missingRefs`가 되고, 원래 파일로 되돌리면 복구됩니다.
- **시스템 백업 → "장비만 복원" → 재시작:** 계산 태그가 남고, register 태그는 다시 연결되며, 값도 정상입니다.

## 4. 장치에 남겨 둔 시험 태그

프론트가 장치에서 바로 확인할 수 있도록 아래 태그를 남겨 두었습니다. 장비 3(메인챔버 온습도조절기)의 레지스터입니다. 필요 없으면 지워도 됩니다.

| id | 종류 | 내용 |
|---|---|---|
| `TEMP` | register | NPV(부호 있음, 배율 0.1) |
| `NOW_STS` | register | NOWSTS(운전상태, rw) |
| `ALSTS` | register | ALSTS(경보상태) |
| `PID_NO` | register | C.PID, 태그 범위 1–10(쓰기 422 확인용) |
| `PID_INH` | register | C.PID, 범위는 레지스터 0–16을 물려받음 |
| `OUT` | register | NMV, 태그 배율 0.01 |
| `RUNNING` | expr | `bitAny(NOW_STS, [0])` |
| `CAN_START` | expr | `and(not RUNNING, ALSTS = 0)` |
| `STATE_TXT` | expr (string) | `select(RUNNING → "RUN", TEMP ≥ 200 → "HOT", "STOP")` |
