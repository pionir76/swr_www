# HMI 화면 저장/불러오기 API — 백엔드 검토 결과 및 조율 사항

> 작성: 2026-10-15
> 상태: **구현 완료** (2026-10-15, 장치 배포됨) — 변경 내용은 `api-changelog.md` 2026-10-15 항목 참고
> 대상 요청서: "HMI 화면 저장/불러오기 API 요청서"

---

## 요청서 검토 결과

설계 방향이 타당하고 기존 백엔드 구조와 잘 맞습니다. 구현 가능합니다.

확인된 사항:

- **저장 원자성** — 이미 사용 중인 SQLite 트랜잭션으로 충족됩니다. 임시 파일 교체 방식은 쓰지 않습니다.
- **content 256KB** — 문제 없습니다. 백업 ZIP 업로드가 이미 더 큰 바디로 들어오고 있어 검증된 경로입니다.
- **화면 id 규칙** — HMI 태그와 같은 검증식(`^[A-Za-z0-9_-]{1,64}$`)을 그대로 재사용합니다. 요청서 내용과 일치합니다.
- **조회 API가 쓰기를 유발하지 않음** — 현재 구조상 자동 충족입니다.
- **동시 편집** — revision 비교 후 저장까지가 단일 스레드에서 처리되므로 중간에 끼어드는 요청 없이 안전합니다.

아래 **2건은 회신이 필요**하고, **5건은 백엔드가 제안대로 확정**하려 합니다.

---

## 회신이 필요한 사항

### 1. 화면 생성/삭제 시 프로젝트 revision 처리가 명세에 없습니다

`POST /api/hmi/screens`와 `DELETE /api/hmi/screens/{id}`는 프로젝트의 `screens` 배열을 변경합니다. 따라서 프로젝트 revision도 올라가야 합니다.

그런데 POST 응답이 `{ "ok": true, "id": "boiler", "revision": 1 }`이고, 이 `revision`은 **새로 만든 화면의 revision**입니다. 프로젝트 revision이 몇으로 올라갔는지 알려주는 값이 없습니다.

이대로면 다음 순서에서 편집기가 막힙니다.

```
1. GET /api/hmi/project          → 프로젝트 revision 2 수신
2. POST /api/hmi/screens         → 화면 추가 (프로젝트 revision은 내부적으로 3이 됨)
3. PUT /api/hmi/project          → 들고 있는 revision 2로 순서 변경 요청
   → 409 revision mismatch
```

화면을 추가한 직후 순서를 조정하는 흐름이 바로 실패합니다.

**제안** — 생성/삭제 응답에 `projectRevision`을 함께 반환합니다.

```json
// POST /api/hmi/screens  → 201
{ "ok": true, "id": "boiler", "revision": 1, "projectRevision": 3 }

// DELETE /api/hmi/screens/{id}  → 200
{ "ok": true, "projectRevision": 4 }
```

첫 화면이라 `startScreen`이 자동 지정된 경우도 이 값으로 알 수 있습니다. 필요하면 `startScreen`도 응답에 포함하겠습니다 — 원하시면 알려주세요.

---

### 2. 마지막 화면을 삭제할 수 없습니다

요청서 규칙상 시작 화면은 삭제할 수 없고(409), `startScreen`은 존재하는 화면이어야 합니다(400).

화면이 1개만 남으면 그 화면이 필연적으로 시작 화면입니다. 시작 화면을 다른 곳으로 옮길 대상도 없으므로 **그 화면은 영구히 삭제할 수 없습니다.** 화면을 전부 비우고 처음부터 다시 만드는 경로가 없어집니다.

또한 빈 프로젝트 상태를 `{ "startScreen": null, ... }`로 정의하셨으므로, `startScreen`에 `null`은 허용되어야 합니다. 현재 명세의 400 규칙과 충돌합니다.

**제안** — 두 가지를 함께 적용합니다.

- 화면이 1개만 남은 상태에서의 DELETE는 **허용**하고, `startScreen`을 자동으로 `null`로 내립니다.
- `PUT /api/hmi/project`의 `startScreen`에 `null`을 **명시적으로 허용**합니다. (화면이 있는 상태에서 null로 바꾸는 것도 허용할지는 알려주세요. 막는 편이 안전하다고 보지만 편집기 흐름에 따라 다를 수 있습니다.)

이렇게 하면 "시작 화면은 삭제 불가" 규칙은 **화면이 2개 이상일 때만** 적용됩니다.

## 백엔드가 제안대로 확정하려는 사항

이견이 없으면 그대로 진행합니다. 문제가 되는 항목이 있으면 알려주세요.

### 3. `title`의 단일 원본은 화면 쪽입니다

`title`이 화면 객체와 프로젝트의 `screens` 배열 양쪽에 나옵니다. 화면 테이블의 `title`을 유일한 원본으로 두고, 프로젝트 조회 시 조합해서 내려줍니다.

따라서 **`PUT /api/hmi/screens/{id}`로 title만 바꿔도 프로젝트 revision은 올라가지 않습니다.** 프로젝트 revision은 이름·시작 화면·화면 순서에만 반응합니다.

### 4. `updatedAt` 포맷

요청서 예시가 `"2026-10-15T11:20:00"`(타임존 없는 로컬 시각)인데, 기존 HMI 태그는 UTC 기준 `CURRENT_TIMESTAMP`를 쓰고 있습니다.

**요청서 예시 형식(ISO-8601 로컬, 타임존 없음)으로 통일**하겠습니다. HMI 태그 쪽도 같은 형식으로 맞출지는 별도로 정리하겠습니다 — 기존 태그 API의 타임스탬프를 화면에 표시하고 있다면 알려주세요.

### 5. 화면 개수 상한은 설정값으로 노출합니다

`config.json`에 `hmi.maxScreens`(기본 50)로 넣습니다. 상한 초과 시 요청서대로 409를 반환하며, 응답에 현재 상한을 함께 담습니다.

```json
{ "error": "too many screens", "maxScreens": 50 }
```

### 6. `content`는 재직렬화해서 저장합니다

받은 JSON을 파싱·검증한 뒤 공백 없는 형태로 다시 직렬화해 저장합니다. 의미는 완전히 보존되지만 **바이트 단위로 보낸 그대로는 아닙니다**(키 순서와 공백이 달라질 수 있음).

프론트가 content의 바이트 원본에 의존하는 로직(해시 비교, 서명 등)이 있으면 알려주세요. 그 경우 원문 그대로 저장하는 방식으로 바꾸겠습니다.

### 7. 413 판정 기준

256KB는 **`content`를 직렬화한 바이트 크기**로 측정합니다. 요청 바디 전체(title 등 포함)가 아닙니다.

## 백엔드가 정해 달라고 하신 항목: 공장 초기화

**HMI 프로젝트·화면·태그를 모두 삭제합니다.**

현재 공장 초기화는 이미 HMI 태그 테이블을 삭제하고 있습니다. 화면만 남기면 삭제된 태그를 참조하는 깨진 화면이 남게 되므로, 함께 지우는 것이 일관됩니다.

---

## 백업/복원

요청대로 백업 ZIP에 HMI 전체를 포함하도록 연결합니다. 현재 `hmi.json` 자리는 빈 객체이고 복원은 미구현 상태인데, 이번에 실제로 채웁니다.

`hmi.json` 구조:

```json
{
  "project": { "name": "...", "startScreen": "main", "order": ["main", "chiller"], "revision": 2 },
  "screens": [ { "id": "main", "title": "...", "revision": 3, "content": { } } ],
  "tags":    [ { "id": "LEVEL_SP", "name": "...", "registerId": 12 } ]
}
```

- 복원의 `options.hmi: true`이면 프로젝트·화면·태그를 복원합니다.
- **복원은 병합이 아니라 전체 교체입니다.** 기존 HMI 데이터를 지우고 백업 내용으로 대체합니다. 병합이 필요하면 알려주세요.
- 백업 포함 여부(`contents.hmi`)와 복원 옵션(`options.hmi`)의 **기본값을 `true`로 바꿀 예정**입니다. 현재는 미구현 상태라 `false`였습니다. 복원 화면에서 체크박스 기본 상태가 바뀌니 참고하세요.
- HMI 태그는 레지스터를 참조하므로, 레지스터를 복원하지 않고 HMI만 복원하면 참조가 깨질 수 있습니다. `options.hmi: true`인데 `options.registers: false`인 조합에서 경고를 반환할지 알려주세요.

## 참고 사항

- 요청서의 "프론트가 전환 시점에 기존 화면 2개를 POST로 옮겨 넣겠다"는 계획대로 진행하시면 됩니다. 백엔드는 초기 데이터를 넣지 않고 빈 프로젝트 상태로 시작합니다.
- 실행 화면의 실시간 값은 기존 `/api/hmi/values`를 그대로 사용하는 것으로 확인했습니다. 이번 API는 폴링 부하가 없습니다.
- `content.format != "whmi.screen"`이면 400을 반환하고, 그 외 내부 구조는 검사하지 않습니다. 위젯이 늘어나도 백엔드 수정은 필요 없습니다.

## 정리

| # | 항목 | 필요한 조치 |
|---|---|---|
| 1 | 생성/삭제 응답에 `projectRevision` 추가 | **회신 필요** |
| 2 | 마지막 화면 삭제 허용 + `startScreen: null` | **회신 필요** |
| 3 | title 원본은 화면 쪽, 프로젝트 revision 무관 | 이견 시 회신 |
| 4 | `updatedAt`은 ISO 로컬 형식 | 이견 시 회신 |
| 5 | `hmi.maxScreens` 설정값(기본 50) | 이견 시 회신 |
| 6 | `content` 재직렬화 저장 | 바이트 원본 의존 시 회신 |
| 7 | 413은 content 크기 기준 | 이견 시 회신 |
| — | 공장 초기화 시 HMI 전체 삭제 | 백엔드 결정 (회신 불필요) |
| — | 복원은 전체 교체, 기본값 `true`로 변경 | 병합 필요 시 회신 |
| — | `hmi` 복원 시 `registers` 미복원 경고 여부 | 회신 요청 |

1·2번 회신을 받으면 바로 구현에 들어갑니다. 3~7번은 회신이 없으면 제안대로 확정합니다.
